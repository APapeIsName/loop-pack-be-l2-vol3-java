> 지금부터 하는 모든 이야기는 **TPS 300 서비스를 운영한다는 가정 하에 일어나는 상상**입니다.
**실제 일어난 일이 아님**을 인지하고 읽어주시면 감사드리겠습니다.

**TL;DR**
> DB는 우리의 친구, 아낌없이 주는 나무입니다. 우리 친구를 오래오래 보고 싶다면 사람들로부터 적당히 과일을 주면서 지켜야 하죠.
>
>인덱스는 **저절로 떨어진 과일**과 같이 나무가 큰 부담없이 줄 수 있습니다.
>
>캐시는 **몰래 과일들을 주워다가 마트에서 파는 것**과 같습니다. 사람들은 굳이 나무로 찾아가지 않아도 과일을 먹을 수 있으니 나무를 괴롭히지 않을 거예요.
>
>이렇게 생각하고 우리는 어떻게 DB가 오래오래 우리 곁에서 살아갈지를 고민하며 지켜야 합니다.

# 크리스마스의 악몽 - 홀리데이 이벤트 그 뒷면에서 일어난 일

안녕하세요, 감성 이커머스 루패션(Loopassion)에서 백엔드 개발을 맡고 있는 페잎입니다. 2025년 크리스마스 시즌, 홀리데이 이벤트가 예상을 훌쩍 뛰어넘는 반응을 얻으면서 TPS가 평소(40~50)의 약 6~7배인 300까지 치솟았습니다. 그 뒷면에서 저희 백엔드 팀에 무슨 일이 있었는지 이야기해보려 합니다.

![AI 생성 이미지입니다.](https://velog.velcdn.com/images/gms72901217/post/92c1d12a-9495-4fda-b27d-f973dbaf63d9/image.png)_AI 생성 이미지입니다. 실제로 제품은 판매하고 있지 않습니다._

저희는 크리스마스 당시 홀리데이 감성 셀렉트 기획전을 진행했습니다. 하프기장 페이크퍼 코트, 모카무스 머플러, 버건디 니트 등 당시 유행하던 제품들과 한정판 커플 파자마 등 다양한 상품들을 메인으로 두었는데요. 저희가 예상하는 수치는 TPS 200 정도였습니다. 이전 빼빼로 데이 때도 DAU는 5만 명, TPS는 130~140 정도까지 올랐던 걸 감안해 예측한 수치였죠.

그 예측은 단단히 잘못된 거라는 걸 깨닫는 건 얼마 걸리지 않았습니다. 오픈 초반 DAU 6만, TPS 100~120 — 속된 말로 "오픈빨" 정도로 생각했습니다.

**근데 수치가 점차 올라가더니 결국 200이란 벽을 뚫어버렸습니다.**

상품 목록 2~3초 지연, 주문 타임아웃, CS 문의 폭주까지... 다행히 로드밸런서를 준비해둬서 빠르게 스케일 아웃해 더 큰 불로 번지지는 않았습니다.

서버를 늘리자 주문 타임아웃 빈도는 줄었습니다. 하지만 상품 목록은 **여전히 2초.** 서버가 늘어나더라도 DB에서 발생하는 문제는 쉽게 해결하지 못했습니다.

저희는 바로 긴급 공지를 통해 서버 불안정 상황을 알렸고, 다행히도 대다수의 사용자분들께서 양해해주셨습니다. 다음에 있을 설날 이벤트에는 이런 일이 없도록 하기 위해 일명 **설날 사수 프로젝트: TPS를 사수하라** 작전을 시작했습니다.

# 장애 회고 — 최적의 응답 속도 40ms를 향하여

바쁘게 장애를 수습한 뒤에는 원인 분석을 진행하기로 했습니다. 그후, 병목 분류와 개선 우선순위를 설정해 이번 기회에 확실하게 조회 병목을 잡아내기로 다짐했습니다.

## 슬로우 쿼리 로그를 까보니

저희는 우선 DB를 의심했습니다. 그래서 슬로우 쿼리를 먼저 까보게 됐습니다. 여기서 충격적인 것을 발견했습니다. 저희 상품 테이블은 10만 건에 달하는 데이터가 있음에도 불구하고, **단 하나의 인덱스도 없었다는 거죠.**

## "쿼리가 느림" vs "쿼리가 너무 많음"

문제는 한 가지가 아니었습니다. 두 종류였는데요. 앞서 말한 **쿼리가 느린 경우**와 앞으로 말씀드릴 **쿼리가 너무 많은 경우**입니다.

**쿼리가 느린 경우** — 상품 목록이 Full Scan을 치고 있었습니다. 인덱스가 없으니까요.

**쿼리가 너무 많은 경우** — 브랜드, 쿠폰, 상품 상세처럼 거의 안 바뀌는 데이터를 매 요청마다 DB에서 읽어오고 있었습니다.

쿼리가 느린 건 **인덱스**로, 많은 건 **캐시**로 해결해보기로 했습니다.

## 그래서 어디부터?

저는 사용자 경험을 제일 우선시하는 개발자로서, 해당 문제가 얼마나 사용자 경험을 헤치고, 더불어 비즈니스적인 가치를 깎아먹는가? 를 중점적으로 잡았습니다. 이에 다음처럼 정리했습니다.

| 순위 | 문제 | 분류 | 해결 방식 |
|------|------|------|-----------|
| 1 | 주문 타임아웃 | 쿼리가 느림 | 인덱스 |
| 2 | 상품 목록 지연 | 느림 + 많음 | 인덱스 + 캐시 |
| 3 | 상품 상세 지연 | 쿼리가 많음 | 캐시 (선별) |
| 4 | 브랜드 반복 조회 | 쿼리가 많음 | 캐시 |
| 5 | 쿠폰 반복 조회 | 쿼리가 많음 | 캐시 |

주문은 저희 비즈니스 모델에서 가장 중요한 핵심 도메인이기에 1순위로 두었고, 나머지 우선순위도 역시 이 주문까지 오기 위한 과정들을 높게 두었습니다.

## 왜 40ms인가

목표가 있어야 개선을 판단할 수 있겠죠. 저희는 사용자가 "즉각적"이라고 느끼는 응답 시간을 기준으로 잡았습니다.

Jakob Nielsen의 연구에 따르면, 사용자가 원인과 결과가 바로 연결된다고 느끼는 임계값은 **100ms**입니다. 여기서 네트워크 왕복(~10ms, AWS 서울 리전 기준)과 프론트엔드 처리(~50ms)를 빼면 백엔드에 남는 예산은 약 **40ms**예요.

```
전체 100ms (사용자 체감 "즉각적")
= 네트워크 왕복 (~10ms)
+ 프론트엔드 처리 (~50ms)
+ 백엔드 응답 (~40ms)
```

**목표: TPS 300에서 주요 API p95 < 40ms.**

이 목표를 향해, 인덱스 설계부터 시작했습니다.

# 인덱스 설계 — EXPLAIN을 맹신하지 말아라

## 문제 쿼리 수집

상품 목록 조회에는 3가지 정렬(인기순, 최신순, 가격순)과 브랜드 필터 유무가 있습니다. 조합하면 총 6가지 쿼리 패턴이 나오는데요.

```sql
-- 전체 목록 (브랜드 필터 없음)
SELECT * FROM product WHERE deleted_at IS NULL ORDER BY likes_count DESC LIMIT 20;
SELECT * FROM product WHERE deleted_at IS NULL ORDER BY created_at DESC LIMIT 20;
SELECT * FROM product WHERE deleted_at IS NULL ORDER BY price LIMIT 20;

-- 브랜드 필터
SELECT * FROM product WHERE deleted_at IS NULL AND brand_id = ? ORDER BY likes_count DESC LIMIT 20;
SELECT * FROM product WHERE deleted_at IS NULL AND brand_id = ? ORDER BY created_at DESC LIMIT 20;
SELECT * FROM product WHERE deleted_at IS NULL AND brand_id = ? ORDER BY price LIMIT 20;
```

인덱스가 하나도 없는 상태에서 이 쿼리들을 EXPLAIN 돌려보면, 전부 `type: ALL`, `Using filesort` — **10만 건 Full Scan**에 정렬까지. 당연히 느릴 수밖에 없었죠.

## EXPLAIN의 함정 — LIMIT이 만들어내는 착각

인덱스를 설계하기 전에, `deleted_at`을 인덱스에 넣어야 하는지부터 고민했습니다. 당연히 "활성화된 상품만 볼 수 있으니까 맨 앞에 둬야지"라고 생각했습니다.

하지만 넣지 않았습니다. 왜냐고요? `deleted_at IS NULL`은 전체의 95%가 매칭돼서, 인덱스에 넣어도 거의 모든 행이 통과합니다. 걸러내는 효과가 거의 없는 거죠. 오히려 정렬 컬럼만 넣은 인덱스가 정렬 순서대로 스캔하다 조건에 맞는 20개를 찾으면 바로 멈추기 때문에 더 빨랐습니다.

우선 `(likes_count DESC)` 인덱스를 하나 걸고 EXPLAIN을 돌려봤습니다.

```
type: index, rows: 20, Extra: Using where
```

`rows: 20` — 딱 필요한 만큼만 읽는 것처럼 보입니다. "괜찮은데?" 싶었어요.

브랜드 필터 쿼리도 돌려봤습니다. `(likes_count DESC)` 인덱스 하나로 `brand_id = ?` 필터까지 처리되는 것처럼 보였고요. `rows: 20`. 전용 복합 인덱스가 필요 없어 보였죠. 이 시점에서 저는 "인덱스 하나면 충분하겠다"라고 판단했습니다.

**근데 이게 거짓말이었습니다.**

## EXPLAIN ANALYZE — 진짜 비용을 보다

EXPLAIN은 옵티마이저의 **추정치**입니다. 실제로 쿼리를 실행하지 않아요. 반면 EXPLAIN ANALYZE는 실제로 쿼리를 돌려서 진짜 읽은 행 수를 보여줍니다. 이걸 돌려봤더니, 숫자가 완전히 달라졌습니다.

**인기순 전체 목록 — 인덱스 하나로 260배:**

| 상태 | EXPLAIN rows | ANALYZE actual rows | actual time |
|------|-------------|-------------------|-------------|
| 인덱스 없음 (Full Scan) | 99,509 | 100,000 | **25.9ms** |
| `(likes_count DESC)` | 20 | 22 | **0.099ms** |

여기까지는 예상대로였습니다. 인덱스 하나로 260배 빨라졌으니까요.

**문제는 브랜드 필터였습니다.**

| 전략 | EXPLAIN rows | ANALYZE actual rows | actual time |
|------|-------------|-------------------|-------------|
| `(likes_count DESC)` 만 | **20** | **7,072** | **11.3ms** |
| `(brand_id, likes_count DESC)` | 238 | **21** | **0.116ms** |

EXPLAIN은 `rows: 20`이라고 했는데, 실제로는 **7,072행**을 읽고 있었습니다. **354배**나 차이가 나요.

왜 이런 일이 벌어졌을까요? `(likes_count DESC)` 인덱스를 순서대로 스캔하면서 `brand_id = 395`인 행을 찾는 건데, 10만 건 중에 해당 브랜드 상품은 230건 정도밖에 없거든요. 인덱스에 띄엄띄엄 흩어져 있으니 20개를 채우기까지 7,072행을 뒤져야 했던 겁니다.

EXPLAIN의 `rows: 20`은 "20행을 **반환**한다"는 뜻이었지, "20행만 **읽는다**"는 뜻이 아니었어요.

반면 `(brand_id, likes_count DESC)` 복합 인덱스는 brand_id = 395를 통해 바로 찾아서 21행만 읽고 끝났습니다. actual time 기준으로는 무려 **97배**나 빨랐었죠.

여러분도 저처럼 EXPLAIN의 rows만 믿으면 안 됩니다. EXPLAIN ANALYZE나 직접 부하 테스트를 꼭 해보시는 걸 추천드립니다. 정말이요.

## 최종 인덱스 설계

3가지 정렬 × 브랜드 필터 유무 = 6가지 쿼리 패턴. 이걸 커버하려면 6개의 인덱스가 필요합니다.

| 정렬 | 인덱스 | 비고 |
|---|---|---|
| 인기순 | `(likes_count DESC)` | 메인 정렬 |
| 최신순 | `(created_at DESC)` | 기본 정렬 |
| 가격순 | `(price)` | |
| 브랜드+인기순 | `(brand_id, likes_count DESC)` | 같은 것부터 비교, 정렬은 그 뒤에 |
| 브랜드+최신순 | `(brand_id, created_at DESC)` | 동일 원리 |
| 브랜드+가격순 | `(brand_id, price)` | 동일 원리 |

복합 인덱스 컬럼 배치 원칙은 `=`(같은지 비교) → `범위 비교` → `ORDER BY`(정렬) 순이에요. `brand_id = ?`는 제일 앞, 정렬 컬럼은 가장 뒤에 두는 이유가 그것이죠. 이렇게 하면 brand_id로 빠르게 특정 브랜드만 찾아낸 뒤 정렬 순서대로 읽을 수 있겠죠?

### 인덱스 적용 전후 비교 (EXPLAIN ANALYZE)

| 쿼리 | Before | After | 개선 |
|---|---|---|---|
| 인기순 | Full Scan, 25.9ms | Index Scan, 0.099ms | **260배** |
| 브랜드+인기순 (단일 인덱스) | actual rows 7,072, 11.3ms | 복합 인덱스 actual rows 21, 0.116ms | **97배** |

인덱스로 쿼리 성능이 **260배** 빨라졌습니다. 하지만 이건 "쿼리가 느린" 문제만 해결한 거예요. "같은 데이터를 동시에 읽는" 문제는 아직 남아있었습니다.

# 캐시 설계 — 인덱스로는 못 지키는 동시 트래픽 방어하기

인덱스로 쿼리는 빨라졌지만, 같은 데이터를 매번 DB에서 읽어오는 건 여전히 낭비입니다. 특히 한정판 상품에 수천 명이 동시에 접속하면 다시 크리스마스의 악몽을 겪는 거죠. 인덱스가 아무리 빠르게 돼 있어도 DB 커넥션 풀에는 한계가 있으니까요.

## 뭘 캐시해야 하는가

처음엔 캐시에 많이 올리는 게 좋은가? 라고 생각했습니다. 하지만 DB 입장에서 캐시는 DB의 상태를 모르는 정적인 데이터와 같아요. 그래서 stale 데이터가 생깁니다. 그렇기에 캐시를 정하는 기준이 필요했고, 저는 다음과 같이 정했습니다.

1. **반복 조회가 빈번한가** — 같은 데이터를 계속 읽는가?
2. **변경 빈도가 낮은가** — 캐시해도 stale 문제가 적은가?

| 데이터 | 반복 조회 | 변경 빈도 | 캐시 |
|--------|----------|----------|------|
| 상품명, 설명, 가격 | 높음 | 거의 없음 (관리자만) | O |
| 재고 | 높음 | 높음 (주문마다) | X |
| 좋아요 수 | 높음 | 높음 (실시간) | X |
| 브랜드 목록 | 매 요청마다 | 거의 없음 | O |
| 쿠폰 템플릿 | 발급마다 | 거의 없음 | O |

패션 커머스 특성상 상품명이나 설명은 등록 후에 쉽게 바뀌지 않습니다. 가격도 프론트엔드에서 처리하기에 고정이고요. 반면 재고는 주문마다, 좋아요는 실시간으로 변하니 캐시에서 제외했습니다.

## Caffeine vs Redis — "서버가 죽으면 어떻게 되는가?"

캐시는 크게 서버 외부에 두냐 내부에 두냐로 나눌 수 있습니다. Spring Boot 권장 캐시는 Caffeine(내부)과 Redis(외부)가 있죠.

저는 이 두 캐시를 사용하는 기준을 두 가지로 잡았습니다.

1. **캐시가 전부 날아가도 DB가 버틸 수 있는가?** — stampede 위험
2. **서버가 여러 대일 때, 서버 간 데이터가 달라도 괜찮은가?** — 정합성

브랜드를 생각해볼까요? 루패션에는 약 500개의 브랜드가 입점해 있는데요. 이 브랜드 캐시가 날아가더라도 DB에 자주 들어오는 요청도 아니고, 선택지가 상품에 비하면 다양하지도 않습니다. 그래서 **Caffeine**에 두기로 했습니다.

상품은 어떨까요? 수만 건의 데이터가, 다양한 사용자에게 동시에 조회됩니다. 수천 요청이 동시에 DB를 치게 되면 **stampede** 현상이 일어나게 되고 이는 장애로 이어지게 됩니다. 그러므로 **Redis**에 두어야 하죠.

### 대상별 캐시 배치

| 대상 | 캐시 | TTL | 이유 |
|---|---|---|---|
| 브랜드 목록 | Caffeine | 10분 | 수백 건, 변경 극히 드묾, 재시작해도 DB 부하 적음 |
| 쿠폰 템플릿 | Caffeine | 10분 | 건수 적고, 재시작 시 DB 부하 적음 |
| 상품 목록 (page 1~3) | Redis | 3분 | 트래픽 대부분이 앞쪽 페이지 집중, 수만 건 |
| 상품 상세 | Redis | 5분 | 핫키 집중 패턴, 수만 건 |

## TTL은 어떻게 잡았나

상품 목록의 TTL을 가장 짧게 잡은 이유가 있어요. 인기순 정렬은 좋아요 수 기준인데, 좋아요가 달릴 때마다 정렬 순서가 바뀔 수 있으니까요. 이걸 매번 evict하면 캐시가 동작을 안 합니다. 3분이면 사용자 입장에서 크게 위화감 없으면서도 자연스럽게 갱신되죠.

| 대상 | TTL | 근거 |
|---|---|---|
| 브랜드/쿠폰 | 10분 | 관리자만 CUD, 변경이 거의 없어서 넉넉하게 |
| 상품 상세 | 5분 | 관리자 수정 시 evict하되, 수정 없어도 자연 갱신 |
| 상품 목록 | 3분 | 좋아요 수 변동이 정렬에 영향 → 상대적으로 짧게 |

## 그렇다면 좋아요는 왜 evict하지 않는가

저희가 사용하는 무효화 전략은 다음과 같습니다.

| 상황 | 전략 | 이유 |
|---|---|---|
| 관리자가 상품/쿠폰/브랜드 수정 | `@CacheEvict` 즉시 삭제 | 의도적 변경 → 즉시 반영 |
| 새 상품 등록 | 목록 캐시 전체 삭제 (`allEntries = true`) | 새 상품이 목록에 안 보이면 안 됨 |
| 좋아요로 likesCount 변경 | 무효화 안 함, TTL 자연 만료 | 아래 설명 |

"좋아요가 달릴 때마다 evict하면 되지 않나?" — 저도 처음엔 그렇게 생각했어요. 근데 테스트해봤더니 그게 더 나빴습니다.

| | 방식 A: 좋아요마다 Evict | 방식 B: TTL 자연 만료 |
|---|---|---|
| 캐시 히트율 | **0%** (매번 미스) | **100%** (전부 히트) |
| DB 부하 | 높음 (매번 DB 재조회) | 낮음 (초기 1회만) |
| 정합성 | 일치 | TTL 만료까지 stale |

"그래도 A가 정합성이 맞잖아" — 맞아요. 근데 동시성 환경에서 테스트해보면 A도 완벽하지 않았습니다.

| 읽기:쓰기 비율 | 방식 A stale 비율 | 방식 B stale 비율 |
|---|---|---|
| 200:5 | **21%** | 92% |
| 100:10 | **45%** | 92% |
| 100:50 | **56%** | 92% |

evict 직전에 읽은 스레드가 옛날 값을 가져가기 때문에, 방식 A를 택해도 stale이 21~56% 발생해요. 어차피 완벽하지 않다면, 캐시가 제대로 동작하는 B가 합리적이라고 판단했습니다.

그리고 프론트엔드에서 내가 누른 좋아요를 즉시 반영하고 캐싱하면 UX적으로도 문제 없다고 생각했습니다.

# 부하 테스트 — 인덱스가 근본, 캐시는 증폭기

인덱스와 캐시를 다 적용한 뒤, k6로 크리스마스 시나리오를 재현했습니다. 근데 단순히 before/after만 비교하면 "뭐가 얼마나 기여했는지"를 알 수 없잖아요. 그래서 인덱스 유무 × 캐시 유무를 독립적으로 측정하는 **2x2 매트릭스 테스트**를 설계했습니다.

- 인덱스 비활성화: 런타임 DROP INDEX
- 캐시 비활성화: `spring.cache.type=none`으로 앱 재시작
- 총 4회 테스트, 각각 독립적으로 측정

## 4번 돌린 결과

**상품 목록** (전체 트래픽의 40%, Full Scan이 발생하던 핵심 쿼리):

| | 캐시 X | 캐시 O |
|---|---|---|
| **인덱스 X** | avg 50.6ms / p95 126ms | avg 66.4ms / p95 184ms **(역효과 +31%)** |
| **인덱스 O** | avg 12.0ms / p95 30ms | avg 9.0ms / p95 22ms |

**상품 상세** (핫키 집중 패턴):

| | 캐시 X | 캐시 O |
|---|---|---|
| **인덱스 X** | avg 10.4ms / p95 32ms | avg 13.9ms / p95 49ms |
| **인덱스 O** | avg 5.0ms / p95 12ms | avg 3.4ms / p95 8ms |

**전체 HTTP** (목록 40% + 상세 35% + 브랜드 25%):

| | 캐시 X | 캐시 O |
|---|---|---|
| **인덱스 X** | avg 25.8ms / p95 90ms | avg 34.4ms / p95 130ms |
| **인덱스 O** | avg 7.5ms / p95 22ms | avg 5.6ms / p95 16ms |

## 이 표에서 읽어야 할 것

### 인덱스만으로 76% 개선 — 당연한 결과

캐시 없이 인덱스만 추가했을 때, 상품 목록 p95가 126ms → 30ms로 떨어졌어요. **-76%.** Full Scan + filesort를 제거한 것만으로 이 정도입니다.

### 인덱스 없이 캐시만 켜면 역효과 — 예상치 못한 결과

상품 목록 avg가 50.6ms → 66.4ms로 오히려 느려졌어요. **+31%.** 캐시 미스가 발생하면 Full Scan(원래 비용)에다가 Redis 직렬화/역직렬화(추가 비용)까지 더해지니까요. 캐시는 근본 원인을 해결하지 못합니다.

### 인덱스 + 캐시 조합이 최적

인덱스만으로 avg 12ms까지 내린 뒤, 캐시를 얹어서 9ms. **추가 25% 개선.** 인덱스가 쿼리를 빠르게 만들어놓으니까 캐시 미스 비용도 작아지고, 그제서야 캐시가 제대로 동작할 수 있었던 거예요.

```
성능 개선 기여도:
  인덱스: ████████████████████ 76%  (기반 — Full Scan 제거)
  캐시:   █████ 추가 25%           (보완 — 반복 조회 차단)
```

# 결론 — 다음 기념일도 무섭지 않다

## 숫자로 보면

| 지표 | Before (인덱스X, 캐시X) | After (인덱스O, 캐시O) | 개선 |
|---|---|---|---|
| 상품 목록 p95 | 126ms | 22ms | **-83%** |
| 상품 상세 p95 | 32ms | 8ms | **-75%** |
| 전체 HTTP p95 | 90ms | 16ms | **-82%** |

목표였던 p95 40ms를 넉넉하게 달성했습니다. 최종 부하 테스트에서는 피크 593 RPS에서도 **p99가 10.92ms** — 목표 대비 약 4배 여유가 있었어요.

다음 시즌 이벤트에서 이전보다 더 많은 트래픽이 몰렸지만, 서버는 버텼습니다. 장애 없이 이벤트를 마무리했고, "크리스마스의 악몽"은 반복되지 않았습니다.

## DB는 지켰는데... 서버가 죽으면?

구조가 단단해지긴 했지만, 아직 남은 과제가 있어요. 만약 서버가 **10분 이상 장애**가 일어난다면 어떨까요?

이번 설날 이벤트는 저에게 있어, 새해 용돈과도 같았습니다. 높은 트래픽을 경험하면서 인덱스와 캐시를 사용해보고 이를 통해 사용자에게 안정적인 UX를 제공하고, 비즈니스적 가치로 이어졌으니까요.

그리고 인덱스의 효율이 엄청나고 **이 기반이 있어야 캐시도 제 노릇을 한다**는 걸 깨달았습니다. 물론 그 과정 속에서 수많은 테스트와 실패, 검증을 통해 저 스스로 나아갈 수 있었습니다.

자 우리는 이제 단단한 성벽을 가졌네요. 근데 이것이 끝은 아닙니다. 결국 성벽은 언젠간 무너지기 마련, 이에 효과적으로 대응하기 위한 전략을 구축했던 내용을 다음주 공유드리도록 하겠습니다. 많관부.
