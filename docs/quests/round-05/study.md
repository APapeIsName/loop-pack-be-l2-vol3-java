# Round 05 - 조회 성능 개선: 인덱싱과 캐싱

## 인덱싱

### 인덱스란?
- 특정 컬럼 값을 **정렬**해서 저장한 별도의 자료구조 (컬럼 값 + 행 포인터)
- 테이블(본문)은 입력 순서대로 저장, 인덱스(색인)는 컬럼 기준으로 정렬
- 정렬되어 있으니 **시작점을 잡아 탐색 범위를 좁힐 수 있다** (Full Scan → ~20번 비교)

### 테이블과 인덱스가 분리된 이유
- 테이블은 물리적으로 **하나의 정렬 순서**만 가질 수 있다
- 여러 컬럼 기준으로 빠르게 조회하려면 컬럼마다 별도의 정렬된 구조가 필요
- Clustered Index: 테이블 자체가 PK 기준 B+Tree로 저장 (InnoDB 기본)

### B-Tree vs B+Tree
- B-Tree: 모든 노드에 데이터(행 포인터) 존재. 위→아래 탐색
- B+Tree: **데이터는 리프에만**, 리프끼리 **linked list로 연결**
  - 범위 조회: 시작점 찾고 → 옆으로 쭉 따라감 (세로 + 가로 = 2차원)
  - 내부 노드에 데이터가 없으니 키를 더 많이 담음 → 트리가 더 얕음 → 디스크 I/O 감소

### 인덱스를 못 타는 경우 - 공통 원리
> **정렬된 순서에서 시작점을 잡을 수 없을 때**

| 케이스 | 왜 시작점을 못 잡나 |
|---|---|
| `WHERE YEAR(created_at) = 2025` | 날짜순 정렬인데 "년도"로는 시작점 못 잡음 |
| `WHERE name LIKE '%가방%'` | 문자열순 정렬인데 "중간 포함"으로는 시작점 못 잡음 |
| `WHERE price * 2 > 30000` | price순 정렬인데 가공된 값으로는 시작점 못 잡음 |

### 복합 인덱스
- (name, price) → name 먼저 정렬, **같은 name 안에서만** price 정렬
- 앞 컬럼이 `=`로 고정되어야 뒤 컬럼의 정렬이 유효
- `WHERE name = '가방' AND price > 10000` → name 고정, price 정렬 유효 ✅
- `WHERE name > '가방' AND price = 10000` → name 범위 → 여러 그룹 넘나듦 → price 정렬 깨짐 ❌

### 커버링 인덱스
- 쿼리에 필요한 모든 컬럼(SELECT, WHERE, ORDER BY)이 인덱스에 포함
- 테이블까지 가지 않고 **인덱스만으로 쿼리 완결** → 디스크 I/O 감소
- `SELECT *`을 지양하는 이유: 커버링 인덱스를 활용할 수 없기 때문

### 인덱스의 트레이드오프
- 조회는 빨라지지만, **쓰기(INSERT/UPDATE/DELETE) 시 인덱스도 갱신** 필요
- 추가 디스크 공간 사용 (컬럼 값 + 포인터)
- 인덱스 설계는 **"어떤 쿼리가 날아올까"를 먼저 생각**하고 결정

## 캐싱

### 캐시란?
- 자주 조회되고 잘 안 변하는 데이터를 **더 빠른 저장소**에 미리 두는 것
- 목적: DB 부하 감소 + 응답 속도 향상 + DB 커넥션 풀 절약

### 캐시 전략

| 전략 | 동작 |
|---|---|
| Cache Aside | 읽기: 앱이 직접 캐시 확인 → Miss 시 DB 조회 → 캐시 저장. 쓰기: DB 갱신 → **캐시 삭제** |
| Read-Through | 읽기: **캐시가 알아서** DB 조회 → 저장 |
| Write-Through | 쓰기: **캐시와 DB 동시에 갱신** |
| TTL | 일정 시간 후 자동 만료 |
| 수동 무효화 | @CacheEvict 등으로 직접 삭제 |
| Refresh-Ahead | 만료 직전에 백그라운드로 미리 갱신 |

### 갱신 시 "삭제"하는 이유
- 갱신하면 DB 쓰기 + 캐시 쓰기가 동시에 일어나야 함 → 하나 실패 시 불일치
- 삭제하면 다음 조회 때 자연스럽게 최신 데이터가 올라옴 → 더 안전

### Local Cache vs Remote Cache (Redis)

| 상황 | 선택 |
|---|---|
| 단일 서버 + 날아가도 괜찮음 | 로컬 캐시 (Caffeine, @Cacheable) |
| 단일 서버 + 캐시 유실 시 DB 부하 큼 | Redis 고려 |
| 분산 서버 | Redis (거의 필수) |

- 로컬 캐시: JVM 메모리, 네트워크 없음, 가장 빠름 (ns)
- Redis: 별도 프로세스, 네트워크 통신, 메모리 기반 (~1ms)
- 2단 캐시 가능: 로컬(L1) → Redis(L2) → DB
- Redis가 병목이 안 되는 이유: 단순 key-value 조회 + 메모리 기반 → 초당 10만건+

### 캐시 장애 패턴

**캐시 스탬피드**: TTL 만료 순간 대량 요청이 동시에 DB로 몰림
- Lock(Mutex): 한 요청만 DB에 가고 나머지는 대기 후 캐시 Hit (Miss일 때만 락 동작)
- Refresh-Ahead: 만료 전 미리 갱신하여 Miss 자체 방지
- TTL Jittering: TTL에 랜덤 시간 추가하여 만료 시점 분산
- Cache Warming: 서버 시작 시 인기 데이터 미리 로드

**캐시 침투**: 존재하지 않는 데이터 반복 요청 → 매번 DB까지 감
- 해결: null 값도 짧은 TTL로 캐싱

### 캐시 키 설계

- 페이징 파라미터도 캐시 키에 포함: `products:shoes:page=1:size=20`
- 소규모 데이터: 전체 캐싱 후 앱에서 페이징 처리 가능
- 대규모 데이터: 페이징 값 포함 필수

**무효화 전략**:

| 전략 | 원리 |
|---|---|
| 버전 키 (Version Key) | 버전 +1 → 새 키로 전환, 기존은 TTL 자연 만료 |
| 태그 기반 | 관련 키에 태그 부여 → 태그 단위 일괄 삭제 |
| 핫 데이터만 캐싱 | page 1~3만 캐싱, 뒤쪽은 DB 직접 |
| 짧은 TTL | 무효화 로직 없이 30초~1분 TTL로 자연 갱신 |

### 페이징: 오프셋 vs 커서

| | 오프셋 | 커서 |
|---|---|---|
| 방식 | `LIMIT 20 OFFSET 40` | `WHERE id > 100 LIMIT 20` |
| 속도 | 뒤 페이지일수록 느려짐 (N개 읽고 버림) | 어디서든 동일 (인덱스 직행) |
| 캐시 영향 | 데이터 추가 시 모든 페이지 밀림 → 전체 무효화 | 기존 커서 캐시 유효 |
| 적합한 UX | 웹 (페이지 번호) | 모바일 (무한 스크롤) |
| 제약 | 없음 | 페이지 점프 불가, 정렬 기준 유니크 필요 |

### 캐시를 걸 데이터 판단 기준

> **"이 값이 N분 전 데이터여도 사용자에게 피해가 있는가?"**

| 질문 | 캐시 O | 캐시 X |
|---|---|---|
| 자주 요청되는가? | 높은 트래픽 | 요청 적음 |
| 자주 변하는가? | 잘 안 변함 | 빈번하게 변함 |
| 정합성이 깨지면? | 좋아요 수 차이 → 괜찮음 | 재고/결제 → 사고 |

- 상품 정보, 카테고리 목록 → 캐시 O
- 좋아요 수 → 캐시 O (짧은 TTL)
- 재고, 결제 금액 → 캐시 X (실시간성 필수)

**실무 흐름**: PO에게 지연 허용 범위 확인(비즈니스) → 트래픽/쿼리 비용 측정(기술) → 적용 후 히트율/응답 시간 검증(데이터)

## Pre-aggregation (사전 집계)

### View vs Materialized View vs 조회용 테이블

| 구분 | 데이터 저장 | 갱신 주체 | 특징 |
|---|---|---|---|
| View | X (쿼리만 저장) | 없음 (매번 실행) | 자주 쓰는 쿼리에 이름 붙인 바로가기. 성능 이점 없음 |
| Materialized View | O (쿼리 결과 저장) | DB (`REFRESH` 명령) | DB가 관리해주는 조회용 테이블 |
| 조회용 테이블 | O (직접 적재) | 내가 (배치/이벤트/코드) | 적재 로직을 직접 설계·구현 |

### View
- **저장된 SELECT문**. 데이터는 없고 쿼리만 DB에 등록
- 조회할 때마다 원본 테이블을 다시 읽어서 실행 → 항상 최신이지만 성능 이점 없음
- 용도: 복잡한 쿼리의 편의성 (북마크)

### Materialized View (MV)
- "Materialize" = 실체화. View의 쿼리 결과를 **진짜 디스크에 저장**
- 원본 쿼리(SQL)를 기억하고 있어서 `REFRESH MATERIALIZED VIEW` 한 줄로 갱신
- DB가 적재를 대신 해주므로 배치/이벤트 로직 불필요

### MV 지원 여부

| DB | MV 지원 |
|---|---|
| PostgreSQL | O |
| Oracle | O |
| MySQL | X |
| MariaDB | X |

- MV 미지원 DB에서 같은 효과 → 조회용 테이블 + 배치/이벤트로 직접 구현

### MV의 트레이드오프
- REFRESH는 **쿼리 전체를 다시 돌리는 무거운 작업**
- 데이터 변경이 빈번하면 refresh 비용이 조회 이점을 삼킴 → 역효과
- **실시간 정합성이 필요하지 않을 때** 사용 (읽기 전용, 사전 집계 용도)

### Pre-aggregation 방법 정리
- 같은 목적(미리 계산해서 조회 성능 개선)을 달성하는 서로 다른 수단:
  - **MV**: DB가 지원하면 가장 편리
  - **조회용 테이블**: 세밀한 제어 필요 시, MV 미지원 DB에서
  - **배치/이벤트 적재**: 조회용 테이블의 데이터를 채우는 구체적 방법

## Caffeine

### Caffeine이란?
- Java 로컬 캐시 라이브러리. JVM 힙 메모리에 데이터를 캐싱
- Spring Boot 공식 권장 로컬 캐시 (CacheManager 인터페이스에 깔끔하게 매핑)
- 단일 책임 (로컬 캐시만), 경량, 자동 설정 → Spring 사상과 일치

### W-TinyLFU (퇴거 정책)
- LRU 약점: 한 번 쓰인 스캔 데이터가 인기 데이터를 밀어냄
- LFU 약점: 과거 인기 데이터가 누적 횟수 때문에 영원히 안 빠짐
- W-TinyLFU = 둘을 **구조적으로 분리**해서 약점 상쇄:
  - **대기실 (Window Cache, ~1%)**: LRU로 관리. 새 데이터 진입
  - **경비원 (TinyLFU 필터)**: 대기실에서 밀려난 놈 vs 메인 홀 최하위, 빈도 비교
  - **메인 홀 (Main Cache, ~99%)**: 빈도 심사 통과한 데이터만 입장
  - Count-Min Sketch가 주기적으로 횟수 반감 → 과거 인기 잊힘
- 핫 데이터는 소수로 유지돼야 → 파레토 법칙, W-TinyLFU가 이를 정교하게 수행

### 경쟁 라이브러리 비교

| | Guava Cache | EhCache | Caffeine |
|---|---|---|---|
| 퇴거 정책 | LRU만 | LRU만 | W-TinyLFU |
| 무게 | 가벼움 | 무거움 | 가벼움 |
| 상태 | 사실상 유지보수 종료 | 오버스펙 | Spring 공식 권장 |

### Caffeine 단점
- 로컬 전용 — 서버 간 캐시 공유 불가
- JVM 힙 메모리 사용 — 캐시 커지면 GC 부담
- 디스크 저장, 분산 캐시 불가 → 그건 Redis 몫

## Cache-Aside 패턴

### Cache-Aside란?
- 캐시가 DB를 모르게 하고, **앱이 중재자로서 캐시와 DB를 각각 제어**하는 패턴
- 캐시 확인 → 미스 → 앱이 DB 조회 → 앱이 캐시에 저장
- `@Cacheable`은 Cache-Aside를 자동화하는 Spring 도구 (수동 if-else와 동일)
- "Aside" = 옆에. 캐시가 메인 흐름 옆에 붙어있는 보조 저장소

### Cache-Aside vs Read-Through
- **미스 났을 때 누가 움직이냐**가 유일한 차이
  - Cache-Aside: 앱이 DB 감
  - Read-Through: 캐시가 DB 감 (로더 등록)

| | Cache-Aside | Read-Through |
|---|---|---|
| 유연성 | 높음 (비즈니스 분기 가능) | 낮음 (로더 고정) |
| 실수 가능성 | 있음 (put 빼먹기 등) | 없음 |
| Stampede 방어 | 직접 구현 | 내장 (Singleflight) |
| 장애 우회 | 가능 (DB 코드 보유) | 어려움 |
| Redis 지원 | O (기본) | X (자체 지원 없음) |

### 쓰기 패턴

| 패턴 | 동작 | 트레이드오프 |
|---|---|---|
| Cache-Aside | DB 쓰고 캐시 삭제 | 단순, 다음 읽기 미스 |
| Write-Through | 캐시+DB 동시 갱신 | 항상 일관, 쓰기 느림 |
| Write-Behind | 캐시만 쓰고 DB 나중에 | 쓰기 빠름, 유실 위험 |

## 캐시 장애 3대 패턴 (심화)

### Cache Stampede (캐시 쇄도)
- 핫 키 만료 시 동시 요청이 DB로 쏟아지는 현상
- **만료 전 / 만료 시점 / 만료 후** 세 지점에서 방어:

| 막는 시점 | 전략 | 핵심 | 한계 |
|---|---|---|---|
| 만료 전 | 확률적 재검증 | TTL 가까울수록 갱신 확률↑, 소수만 갱신 | 비결정적, 정확히 1회 보장 불가 |
| 만료 시점 | Jitter | TTL = base + random(0, max) | 핫 키 단일 만료엔 무력 |
| 만료 후 | 분산 락 (Redis SETNX) | 1명만 DB, 나머지 대기 | 대기 지연, 락 인프라 의존 |

- **캐시 워밍**: 트래픽 시점을 미리 아는 경우 (선착순 등) 미리 적재 → 미스 자체 방지
- 실무: Jitter 기본 + 핫 키는 분산 락 + 변경 적은 건 확률적 재검증

### Cache Penetration (캐시 관통)
- **없는 키** 반복 요청 → 매번 캐시 미스 → 매번 DB 미스 → 무한 반복
- 캐시 방패가 관통당하는 현상

| 해결 | 동작 | 적합 상황 |
|---|---|---|
| Null 캐싱 + 짧은 TTL | "없음" 자체를 캐싱 (60초 등) | 같은 키 반복 공격 |
| Bloom Filter | 비트 배열로 존재 여부 판별 ("없다"가 100% 확실) | 매번 다른 키 공격 |
| 입력 검증 | 음수 ID 등 사전 차단 | 첫 번째 방어벽 |

- Null 캐싱 TTL을 너무 길게 잡으면 → 실제 데이터 생성 시 반영 안 됨

### Cache Avalanche (캐시 눈사태)
- **Stampede의 대규모 버전**: 다수 키 동시 만료 or 캐시 서버 다운
- Jitter로 동시 만료 방지
- 서버 다운은 Jitter로 못 막음 → Cache HA(Sentinel/Cluster) + 서킷 브레이커 + 캐시 워밍

## 씨앗 문장

- **인덱싱**: 인덱스는 특정 컬럼 값을 B+Tree로 정렬 저장한 별도 구조로, 정렬에서 시작점을 잡아 탐색 범위를 좁히는 것이다.
- **캐싱**: 캐시는 자주 조회되고 잘 안 변하는 데이터를 더 빠른 저장소에 두어 DB 접근 자체를 생략하는 것이며, 핵심 문제는 데이터 정합성(무효화)과 비즈니스 판단이다.
- **통합**: 인덱싱은 DB 내부에서 탐색을 줄이고, 캐싱은 DB 외부에서 조회 자체를 줄인다. 둘 다 조회 성능 개선이지만 레이어와 트레이드오프가 다르다.
- **MV**: MV는 View의 쿼리 결과를 실체화해서 저장해두는 것이다. DB가 갱신을 대신 해주는 조회용 테이블이며, 실시간 정합성이 필요 없는 조회 성능 최적화에 쓴다.
- **Caffeine**: Caffeine은 W-TinyLFU라는 LRU→LFU 이중 필터링 알고리즘 덕분에 히트율이 높고, Spring이 단일 책임·유연한 인터페이스·최고 히트율을 보고 공식 권장하는 로컬 캐시 라이브러리다.
- **Cache-Aside**: Cache-Aside는 캐시가 DB를 모르게 하고, 앱이 중재자로서 캐시와 DB를 각각 제어하는 패턴이다. 이로써 앱이 비즈니스 판단(무엇을 캐시할지, 언제 무효화할지)을 직접 할 수 있다.
- **Cache Stampede**: Cache Stampede는 캐시 미스 시 동시 요청이 DB로 쏟아지는 현상이고, 만료 전(확률적 재검증), 만료 시점(Jitter), 만료 후(분산 락) 세 지점에서 각각의 트레이드오프를 갖고 방어한다.
- **Cache Penetration**: Cache Penetration은 캐시가 영원히 Miss 처리될 수 있게 없는 값을 반복 요청하는 공격으로, Null 캐싱(짧은 TTL)이나 Bloom Filter로 방어한다.
- **Cache Avalanche**: Cache Avalanche는 다수 키 동시 만료 or 서버 다운으로 대규모 Stampede가 발생하는 현상이며, Jitter와 Cache HA로 방어한다.
