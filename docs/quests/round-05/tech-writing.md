## 챕터별 작성 가이드

### 챕터 1. 크리스마스의 악몽
- **상태**: 블로그 초안 작성 완료 (기존 draft 있음)
- **핵심**: 장애 상황의 긴박감, 단계적 대응, 근본 해결 필요성
- **수정 사항**: "경위서" → "포스트모템/장애 회고"로 변경

### 챕터 2. 문제 분석
- **핵심 메시지**: 문제를 정의하지 않으면 해결도 없다
- **흐름**:
  1. k6로 300 TPS 재현 → before 수치 제시
  2. 슬로우 쿼리 로그에서 문제 쿼리 식별
  3. 병목 분류: "쿼리가 느림" vs "쿼리가 너무 많음"
  4. 우선순위: 주문 딜레이 > 상품 목록 > 상품 상세 > 브랜드 > 쿠폰
  5. 각 병목에 맞는 해결 방식 제시
- **쓰는 톤**: "슬로우 쿼리 로그를 까보니 상품 목록이 full scan을 치고 있었다"
- **성능 목표 근거**: Jakob Nielsen 100ms → 역산 → 백엔드 50ms

### 챕터 3. 인덱스 설계
- **핵심 메시지**: 인덱스 먼저, 페이지네이션은 그 다음
- **흐름**:
  1. 대상 쿼리 수집
  2. EXPLAIN 돌림 → "rows 20이네, 괜찮은데?" (LIMIT의 함정)
  3. EXPLAIN ANALYZE → "actual rows 수만 건, filesort!" (거짓말 들통)
  4. 깨달음: LIMIT 빼고 봐야 진짜 비용이 보인다
  5. 인덱스 설계: = → 범위 → ORDER BY 원칙
  6. EXPLAIN ANALYZE after: type ALL → ref, filesort 제거
  7. 페이지네이션은 인덱스가 정렬 보장한 뒤에 얹는다
- **쓰는 톤**: "처음엔 EXPLAIN만 보고 괜찮다고 생각했다. 하지만..."
- **실측 데이터**: full scan 25.9ms → 인덱스 0.1ms (260배)

### 챕터 4. 캐시 설계
- **핵심 메시지**: 캐시 위치는 "죽었다 살아나도 괜찮은가?"로 결정한다
- **흐름**:
  1. 인덱스로 쿼리는 빨라졌지만, 같은 데이터를 매번 DB에서 읽는 건 낭비
  2. Caffeine vs Redis — 뭐가 다른가?
     - 단일 서버에서는 사실 차이 없음
     - 하지만 서버가 죽으면? → stampede 관점
  3. 기술 선택 기준: 건수가 적어서 재시작해도 DB가 버티면 → Caffeine
  4. 대상별 배치: 브랜드/쿠폰 → Caffeine, 상품 → Redis
  5. 상품 상세 선별 캐시: 이름/설명/가격만 (재고/좋아요 제외)
  6. 캐시 히트율 측정 결과
- **쓰는 톤**: "처음엔 전부 Redis에 넣으려 했다. 근데 브랜드가 수백 건인데 굳이?"

### 챕터 5. 부하 테스트
- **핵심 메시지**: 인덱스가 기반, 캐시는 그 위의 추가 최적화
- **흐름**:
  1. 캐시 적용 후 DB 호출 횟수 비교
  2. k6 300 TPS 전체 before/after
  3. 핵심 발견: "인덱스 없이 캐시만 켜면 역효과" (실측 데이터)
- **실측 데이터**: 인덱스만 76% 개선, 캐시 추가 25% 개선

### 챕터 6. 결론
- **핵심 메시지**: 단단해졌지만, 진짜 장애 상황은?
- **흐름**:
  1. 숫자 요약 (before/after)
  2. 다음 시즌 더 많은 트래픽이 왔지만 버텼다
  3. 근데 서버가 죽으면? → Caffeine stampede, 단일 서버 SPOF
  4. 다음 과제: resilience (회복탄력성)
