# Final Scenario — Round 05

## 배경

크리스마스 시즌, 평시 TPS(40~50) 대비 약 6배(300 TPS)의 트래픽이 발생.
인덱스도 없었고 캐시도 없었다. 급한 불은 스케일아웃 + DB 스케일업으로 껐다.
"다음엔 이러지 말자" — 그렇게 개선 프로젝트가 시작됐다.

### 성능 목표

> 사용자가 "즉각적"이라고 느끼는 100ms (Jakob Nielsen) 에서
> 네트워크 왕복(~20ms) + 프론트 렌더링(~30ms)을 빼면
> **백엔드 응답 예산은 ~50ms.**
>
> 목표: **TPS 300에서 주요 API p95 < 50ms**

## 챕터 구성

### 챕터 1. 크리스마스의 악몽 (배경/동기)
- 평시 TPS 40~50 → 크리스마스 TPS 300~310
- 상품 목록 2~3초 지연, 주문 타임아웃, DB CPU 85%
- 긴급 스케일아웃(2→4대) + DB 스케일업으로 버팀
- "다시는 이러지 말자" → 개선 계획 수립

### 챕터 2. 문제 분석
1. **부하 재현** — k6로 150 TPS 시나리오 재현, before 수치 확인
2. **슬로우 쿼리 식별** — 느린 쿼리 TOP N, EXPLAIN ANALYZE로 full scan 증거 확보
3. **병목 분류** — 쿼리가 느린 문제 vs 쿼리가 너무 많은 문제
4. **문제 우선순위 & 해결 방식 제시**

| 순위 | 문제 | 해결 방식 | 분류 |
|------|------|-----------|------|
| 1 | 주문 딜레이 | 인덱스 | 쿼리가 느림 — 읽기 지연이 락 점유 시간 늘림 → 타임아웃 |
| 2 | 상품 목록 | 인덱스 + 핫 아이템 캐시 | 느림 + 많음 — 트래픽 입구, full scan + 반복 조회 |
| 3 | 상품 상세 | 선별 캐시 (기본 정보만) | 쿼리가 많음 — 전체 캐시 비현실적 |
| 4 | 브랜드 반복 조회 | 캐시 | 쿼리가 많음 — 거의 안 바뀌는 데이터 |
| 5 | 쿠폰 반복 조회 | 캐시 | 쿼리가 많음 — 주문/목록에서 매번 조회 |

#### 상품 상세 캐시 선별 기준
| 데이터 | 캐시 | 이유 |
|--------|------|------|
| 상품명, 설명 | O | 패션 특성상 한번 등록하면 안 바뀜 |
| 가격 | O | 할인 개념이 백엔드에 없으므로 고정 |
| 브랜드 ID | — | 브랜드 캐시가 따로 있으니 ID만 보유 |
| 재고 | X | 주문마다 변동 |
| 좋아요 수 | X | 실시간 변동 |

### 챕터 3. 인덱스 설계 — 쿼리 최적화의 정석

> 핵심 메시지: **인덱스 먼저, 페이지네이션은 그 다음.** DB 쿼리 최적화는 이 순서로 진행한다.

1. **대상 쿼리 수집** — 슬로우 쿼리에서 뽑은 문제 쿼리 나열
2. **EXPLAIN — LIMIT의 함정**
   - LIMIT이 포함된 쿼리를 EXPLAIN 돌리면 rows 예측이 낮게 나옴
   - "괜찮아 보이는데?" → 거짓말. 실제로는 전체 스캔 후 잘라내는 것
3. **EXPLAIN ANALYZE — 진짜 비용 확인**
   - 실제 실행해보면 actual rows 수만 건, filesort 발생
   - EXPLAIN의 예측과 실제 실행의 괴리를 증명
4. **인덱스 설계 근거**
   - 컬럼 배치 원칙: `=` (등치) → `범위` → `ORDER BY`
   - WHERE/ORDER BY 컬럼 나열 → 원칙에 따라 배치
5. **EXPLAIN ANALYZE — after**
   - 인덱스 적용 후 재검증
   - type: ALL → ref/range, filesort 제거 확인
6. **페이지네이션은 마지막에 얹는다**
   - 인덱스가 정렬을 보장한 뒤 LIMIT을 걸어야 진짜 효과
   - 인덱스 없는 LIMIT은 "전체 정렬 후 자르기"일 뿐

### 챕터 4. 캐시 설계 — DB 부하를 줄여라

> 핵심 메시지: **캐시 위치는 "죽었다 살아나도 괜찮은가?"로 결정한다.**

#### 4-1. 기술 선택 기준

| 기준 | Caffeine (로컬) | Redis (원격) |
|------|-----------------|-------------|
| 속도 | JVM 힙, ns 단위 | 네트워크 + 직렬화, ms 단위 |
| 서버 재시작 시 | 캐시 소멸 → stampede 위험 | 캐시 유지 → 안전 |
| 선택 조건 | 건수 적어서 stampede 와도 DB가 버팀 | 건수 많아서 stampede 오면 DB 과부하 |

#### 4-2. 대상별 캐시 배치

| 대상 | 캐시 | 이유 |
|------|------|------|
| 브랜드 | Caffeine | 수십~수백 건, 거의 안 바뀜, 재시작해도 DB 부하 미미 |
| 쿠폰 | Caffeine | 공용(개인화 아님) 쿠폰, 건수 적음, 같은 논리 |
| 상품 목록 (핫 아이템) | Redis | 수십만 건, stampede 시 DB 과부하 |
| 상품 상세 (기본 정보) | Redis | 수십만 건, 선별 캐시 (이름/설명/가격만) |

#### 4-3. 상품 상세 캐시 선별 기준 (챕터 2에서 정의)
- 캐시 O: 상품명, 설명 (패션 특성상 불변), 가격 (할인 개념 없음)
- 캐시 X: 재고 (주문마다 변동), 좋아요 수 (실시간 변동)
- 브랜드 ID만 보유 → 브랜드 캐시가 별도로 존재

### 챕터 5. 부하 테스트 — before/after 검증

1. **캐시 적용 후 DB 호출 횟수 비교**
   - 캐시 전: 요청당 N번 DB 조회
   - 캐시 후: 히트 시 DB 조회 0
2. **k6 전체 부하 테스트 — 최종 before/after**
   - 챕터 1의 300 TPS 시나리오를 다시 돌림
   - 인덱스 + 캐시 전체 적용 상태에서 측정
   - 응답시간, 에러율, 처리량 비교
