## 실험 설계

### 무대 세팅

- Spring Boot 3.4.4 + MySQL 8 + Redis + Kafka
- 좌석(쿠폰) N장, 참가자 M명
- 참가자 중 1명은 나 (브라우저에서 직접 클릭)
- 나머지는 봇 (Python asyncio, 정규분포 지연으로 현실적 트래픽 시뮬레이션)

### 왜 정규분포?

실제 예매에서 사람들이 동시에 접속하지만, 정확히 같은 밀리초에 도착하진 않는다.
대부분은 오픈 직후 0.2~0.8초 사이에 몰리고, 소수만 빠르거나 느리다.

```
0.0s  ■■
0.2s  ■■■■■
0.5s  ■■■■■■■■■■■■  ← 피크
0.8s  ■■■■■
1.5s  ■
```

### 세 가지 방식

같은 상황을 세 가지 다른 방식으로 처리해본다.

| 방식 | 한 줄 설명 |
|------|-----------|
| DB 비관적 락 | 줄 세우기. 한 명씩 처리. |
| Kafka 비동기 | 접수만 받고 나중에 처리. |
| Redis 원자 카운터 | 번호표 뽑기. 초고속. |

## Chapter 1: "설마 이 정도는 되겠지"

📌 시나리오: 여유로운 경쟁 (경쟁률 낮음)
📌 전략: db-lock
📌 봇 수 / 좌석 수

### 구현 핵심

```java
// SELECT * FROM fcfs_coupon WHERE id = ? FOR UPDATE
FcfsCoupon coupon = repo.findByIdForUpdate(couponId);
if (coupon.isSoldOut()) → 실패
coupon.incrementIssuedCount();
issuedCouponRepo.save(...)
```

한 명이 처리될 때까지 나머지는 전부 대기. 은행 창구 1개에 줄 서는 것과 같다.

### 결과

📌 봇 결과 (성공/실패 수)
📌 내가 성공했는가?
📌 응답 시간
📌 서버 로그 캡처

## Chapter 2: "현실은 이랬다"

📌 시나리오: 치열한 경쟁 (경쟁률 높음)
📌 전략: db-lock
📌 봇 수 / 좌석 수

### 결과

📌 봇 결과
📌 내가 성공했는가?
📌 타임아웃 / 에러 로그
📌 커넥션 풀 상태

### 왜 터졌는가?

```
999명이 동시 도착
  → SELECT FOR UPDATE → 1번만 통과, 998명 대기
  → 각각 커넥션 1개씩 점유
  → 커넥션 풀 20개 → 21번째부터 대기열
  → 대기열도 꽉 참 → Connection timeout
```

내가 콘서트 예매에 실패한 이유가 이거였을까?
서버가 느린 게 아니라, 줄이 너무 긴 거였다.

## Chapter 3: "다른 방법이 있다던데"

### Kafka — 접수만 받고 나중에 처리

📌 시나리오: 같은 경쟁률
📌 전략: kafka

```java
// API 응답은 즉시
kafkaTemplate.send("fcfs-coupon-issue", payload);
return "요청 접수됨";

// 뒤에서 순차 처리
@KafkaListener(topics = "fcfs-coupon-issue")
void consume(payload) {
    if (soldOut) return;
    save(IssuedCoupon);
}
```

### 결과

📌 봇 결과 — 전원 "요청 접수됨" (성공인 척)
📌 실제 발급 수 확인
📌 전부 처리되기까지 걸린 시간

### 느낀 점

📌 "버티긴 하는데... 나 된 거야 안 된 거야?"
서버는 안 터졌다. 하지만 유저 입장에서는 답답하다.
실제 예매 사이트에서 "대기 중입니다..." 가 이 방식이었을 수도.

---

### Redis — 번호표 뽑기

📌 시나리오: 같은 경쟁률
📌 전략: redis

```java
Long count = redis.increment("fcfs:" + couponId + ":count");
if (count > totalQuantity) → "소진"
save(IssuedCoupon);
return "발급 완료!";
```

### 결과

📌 봇 결과
📌 내가 성공했는가?
📌 응답 시간 (vs DB 락 비교)
📌 정합성 확인: 실제 DB 발급 수 == Redis 카운트?

### 느낀 점

📌 "빠르다. 근데 완벽한가?"
Redis INCR은 원자적이라 초고속. 하지만 Redis에서 번호표를 받고 DB 저장이 실패하면?
카운트와 실제 발급 수가 어긋날 수 있다.

## 마치며

### 은탄환은 없다

- DB 락: 단순하고 정합성 확실하지만, 대량 트래픽에 취약
- Kafka: 서버는 안전하지만, 유저는 불안
- Redis: 빠르고 안정적이지만, 정합성 관리 필요

실제 서비스에서는 이것들을 조합한다.
Redis로 빠르게 걸러내고, Kafka로 안정적으로 처리하고, DB로 최종 기록.
