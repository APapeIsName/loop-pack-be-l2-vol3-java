## 시뮬레이션을 만들어봤다

### 무대 세팅

17시 정각. 7명의 멘티가 동시에 신청 버튼을 누릅니다. 자리는 1개.

이 상황을 직접 재현해보고 싶었습니다. 그래서 간단한 선착순 쿠폰 발급 시스템을 만들었습니다. 쿠폰이 좌석이고, 봇이 다른 멘티들입니다. 저는 브라우저에서 직접 클릭하고요.

- **서버**: Spring Boot 3.4.4 + MySQL 8 + Redis + Kafka
- **쿠폰(좌석)**: N장 (라운드마다 조절)
- **참가자**: 봇 M마리 + 나 1명
- **봇**: 서버 내부에서 HTTP 요청을 쏘는 가상 스레드
- **나**: 브라우저에서 "쿠폰 받기" 버튼을 직접 클릭

봇은 서버와 같은 머신에서 `localhost`로 HTTP 요청을 쏩니다. 순수하게 **"서버가 동시 요청을 어떻게 처리하는가"**에 집중할 수 있는 환경입니다.

### 봇은 어떻게 행동하는가

실제 예매 상황에서 7명이 정확히 같은 밀리초에 클릭하진 않잖아요? 대부분은 오픈 직후 0.1~0.5초 사이에 몰리고, 일부는 살짝 빠르거나 느립니다.

```
0.0s  ■■
0.1s  ■■■■■
0.3s  ■■■■■■■■■■■■  ← 대부분 여기
0.5s  ■■■■■
0.8s  ■
```

그래서 봇마다 정규분포 기반의 랜덤 지연을 줬습니다. 그리고 하나 더 — 실제 예매 사이트에서 버튼을 누르면 "접속 대기 중..."이 뜨면서 잠깐 블로킹되죠? 저도 그걸 넣었습니다. 봇은 이 대기 없이 바로 요청하고, 저만 1~3초를 기다립니다. 현실에서 인간이 가지는 핸디캡 그대로요.

### 처리 방식

처리 방식은 가장 확실한 걸로 골랐습니다. DB 비관적 락 — `SELECT FOR UPDATE`. 한 명이 처리될 때까지 나머지는 줄 서서 기다리는 방식입니다. 느릴 수 있지만, 적어도 정확하니까요.

```java
FcfsCoupon coupon = repo.findByIdForUpdate(couponId);  // 내 차례까지 대기
if (coupon.isSoldOut()) return "소진";
coupon.incrementIssuedCount();
issuedCouponRepo.save(...);
// 커밋 → 락 해제 → 다음 사람
```

은행 창구 1개에 7명이 줄 서는 것과 같습니다.

## Chapter 1: 멘토링 상황을 재현해보자

우선 저는 가장 간단하면서 중요한 멘토링 예약부터 정복해보기로 했습니다. 멘토링은 한 멘토님당 한 팀만 배정받을 수 있습니다. 이에 4주차에 배운 락을 사용해 구현했습니다. 굳이 비관적 락을 사용한 이유는 잠시 후 말씀드리겠습니다. 그리고 Python의 `aiohttp` 라이브러리를 활용해 실제 HTTP로 접근하는 봇들과 경쟁하는 흥미진진한 상황도 추가했죠.

### 1:4 — 인기 멘토, 최대 경쟁

인기 멘토분의 세션이면 7팀 중 최대 4팀이 동시에 신청합니다. 최악의 경우부터 해보죠. 자리 1개에 4명.

| 항목 | 값 |
|------|-----|
| 성공 / 실패 | 1 / 3 |
| avg 응답시간 | 15ms |
| p95 응답시간 | 25ms |
| 에러 | 0건 |

...너무 여유롭습니다. avg 15ms, 에러 0건. 4명이 동시에 눌러도 순식간에 처리됩니다. "뭐야 선착순 시스템 별거 아니잖아?"

멘토링 규모에서는 DB 비관적 락으로 충분합니다. 근데 멘토링은 최대 4명이니까 이 정도지, 실제 콘서트 예매처럼 수천 명이 몰리면 어떻게 될까요?

### 궁금해서 올려봤다 — 100:1000

멘토링 상황에서 벗어나서, 그냥 한번 올려봤습니다. 쿠폰 100장에 봇 1000마리. 경쟁률 10:1.

| 항목 | 값 |
|------|-----|
| 봇 성공 / 실패 | 100 / 900 |
| 에러 | 0건 |
| avg 응답시간 | **331ms** |
| p95 응답시간 | **383ms** |
| max 응답시간 | 459ms |

터지진 않았습니다. 정합성도 완벽합니다. **근데 평균 331ms.**

7명일 때는 몰랐는데, 1000명이 줄 서니까 보이기 시작합니다. 한 명씩 처리하는 구조에서는 뒤에 선 사람일수록 오래 기다릴 수밖에 없다는 것.

"느리지만 정확하다" — 이게 DB 비관적 락의 한계인 건지, 아니면 더 나은 방법이 있는 건지. 궁금해지기 시작했습니다.

## Chapter 2: 다른 방법을 찾아보자

DB 비관적 락의 "줄 서기" 방식이 느린 건 알겠습니다. 그러면 다른 방법은 뭐가 있을까요?

찾아보니 크게 세 가지가 더 있었습니다.

| 방식 | 비유 | 핵심 |
|------|------|------|
| Redis 분산 락 | 화장실 1칸 | DB 대신 Redis에서 줄 서기 |
| Kafka 비동기 | 접수 창구 | 일단 접수, 나중에 처리 |
| Redis 카운터 | 번호표 기계 | 줄 안 섬. 번호표 뽑고 끝 |

같은 조건(쿠폰 100장, 봇 1000마리, 10:1)으로 전부 돌려봤습니다.

### Redis 분산 락 — "DB 대신 Redis에서 줄 서면 빠르지 않을까?"

DB가 아니라 Redis에서 잠금을 거는 방식입니다. Redis가 빠르니까 줄 서는 것도 빠르지 않을까?

```java
Boolean acquired = redis.setIfAbsent("lock:" + couponId, "locked", 3초);  // SETNX
if (acquired) {
    try { 발급 처리 }
    finally { redis.delete(lockKey); }  // 잠금 해제
} else {
    50ms 후 재시도...  // 최대 50번
}
```

| 항목 | DB 비관적 락 | Redis 분산 락 |
|------|-------------|-------------|
| 성공 | 100 | **141** |
| avg | 331ms | **529ms** |
| p95 | 383ms | **695ms** |
| max | 459ms | **1087ms** |

...더 느려졌습니다. 그리고 성공이 141건? 쿠폰은 100장인데?

**초과 발급이 발생했습니다.** 락을 잡고 풀고를 반복하는 사이에 타이밍이 겹치면서 100장 이상이 발급된 겁니다. 빠를 줄 알았는데 느리기까지 하고, 정합성도 깨졌습니다.

### Kafka — "접수만 받으면 서버가 안 터지지 않을까?"

발상을 바꿔봤습니다. 줄을 세우지 말고, 일단 접수만 받는 거예요. "요청 접수됐습니다!" 하고 바로 응답한 뒤, 뒤에서 Kafka Consumer가 순서대로 처리합니다.

```java
// API — 즉시 응답
kafkaTemplate.send("fcfs-coupon-issue", payload);
return "요청이 접수되었습니다";

// Consumer — 뒤에서 순차 처리
@KafkaListener(topics = "fcfs-coupon-issue")
void consume(payload) {
    if (soldOut) return;
    issuedCouponRepo.save(...);
}
```

| 항목 | DB 비관적 락 | Kafka |
|------|-------------|-------|
| 성공 | 100 | **1000 (전원 "접수됨")** |
| avg | 331ms | **2ms** |
| p95 | 383ms | 7ms |

**avg 2ms.** 어마어마하게 빠릅니다. 1000명 전원 "성공"이에요.

...근데 진짜 성공인 건가요? 쿠폰은 100장인데 1000명이 "접수됐습니다"를 받았습니다. 실제로 발급된 건 100장뿐이에요. 나머지 900명은 **조용히 버려집니다.** 나도 그 900명 중 하나일 수 있어요.

"됐나? 안 됐나?" — 모릅니다. 실제 예매 사이트에서 "대기 중입니다..."를 보면서 불안했던 기억, 이게 바로 그 방식이었을 수도 있습니다.

### Redis 카운터 — "줄을 안 서면 되는 거 아냐?"

마지막으로, 아예 줄을 없애봤습니다. Redis `INCR` 명령어로 번호표를 뽑는 방식입니다. 1000명이 동시에 요청해도 Redis가 원자적으로 1, 2, 3... 번호를 매겨줍니다. 100번까지는 통과, 101번부터는 "소진".

```java
Long count = redis.increment("fcfs:" + couponId + ":count");
if (count > totalQuantity) return "소진";
issuedCouponRepo.save(...);
return "발급 완료!";
```

| 항목 | DB 비관적 락 | Redis 카운터 |
|------|-------------|-------------|
| 성공 | 100 | 100 |
| avg | 331ms | **3ms** |
| p95 | 383ms | **8ms** |
| max | 459ms | **31ms** |

**avg 3ms.** Kafka만큼 빠르면서, 즉시 "발급 완료!" 또는 "소진"을 알려줍니다. 정합성도 정확히 100장.

## Chapter 3: 그래서 뭘 써야 해?

4가지 전략을 같은 조건(쿠폰 100장, 봇 1000마리)으로 돌린 결과입니다.

| | DB 비관적 락 | Redis 분산 락 | Kafka 비동기 | Redis 카운터 |
|---|---|---|---|---|
| 비유 | 은행 창구 1개 | 화장실 1칸 | 접수 창구 | 번호표 기계 |
| 성공 | 100 | 141 ⚠️ | 1000 (전원 접수) | 100 |
| avg 응답시간 | **331ms** | **529ms** | **2ms** | **3ms** |
| p95 응답시간 | 383ms | 695ms | 7ms | 8ms |
| 에러 | 0건 | 0건 | 0건 | 0건 |
| 정합성 | ✅ 완벽 | ❌ 초과 발급 | ✅ (뒤에서) | ✅ 완벽 |
| 즉시 결과 확인 | ✅ | ✅ | ❌ 모름 | ✅ |

눈에 띄는 것들:

- **DB 락 vs Redis 카운터**: 331ms vs 3ms. **110배 차이.**
- **Redis 분산 락**: 가장 느리고, 초과 발급까지. 이 상황에서는 최악.
- **Kafka**: 가장 빠르지만, "됐는지 모른다"는 치명적 UX 문제.
- **Redis 카운터**: 빠르고, 정확하고, 즉시 알려줌. 이 조건에서는 최선.

## 마치며

### 은탄환은 없다

📌 (표현은 내 스타일로 바꿀 예정)

Redis 카운터가 최고인 것 같지만, 완벽하진 않습니다. Redis에서 번호표를 받고 DB 저장이 실패하면? 카운트와 실제 발급 수가 어긋날 수 있습니다.

- **DB 비관적 락**: 단순하고 정합성 확실하지만, 느리다
- **Redis 분산 락**: DB 부담을 줄이려 했지만, 이 시나리오에서는 오히려 역효과
- **Kafka**: 서버는 안전하지만, 유저는 불안하다
- **Redis 카운터**: 빠르고 정확하지만, DB 정합성 관리가 별도로 필요하다

### 실제로는 어떻게 하나?

시뮬레이션에서는 전략을 하나씩 분리해서 돌려봤지만, 실제 서비스에서는 이것들을 **조합**합니다.

**배달의민족 빼빼로데이 (2016)** — 선착순 1,111명 쿠폰 이벤트에서 Redis 리플리카 지연으로 **초과 발급**이 발생했습니다. 마스터에 INCR하고 리플리카에서 읽는 구조에서 복제 지연이 생긴 거예요. 우리 시뮬레이션에서 Redis 분산 락이 141장을 발급한 것과 본질적으로 같은 문제입니다. 교훈: 선착순처럼 정확한 수량 제한이 필요하면, 읽기/쓰기 모두 마스터에서 처리하거나 Lua 스크립트로 원자적 판정을 해야 합니다.

**여기어때 네고왕 (선착순 쿠폰)** — 순간 최대 접속자 28,800명, TPS 3,600+. 이 규모를 Redis 단독도, Kafka 단독도 아닌 **Redis(즉시 자격 판정) + Kafka(비동기 DB 발급)** 조합으로 처리했습니다. 우리 시뮬레이션에서 분리해서 본 두 전략의 장점만 합친 거죠. 실제로 이 프로젝트의 선착순 쿠폰 발행 코드도 같은 구조입니다.

### 봇은 법으로도 막는다

시뮬레이션에서 봇이 너무 쉽게 이기는 걸 보면서 느꼈을 겁니다 — "이러면 매크로 쓰는 사람한테 절대 못 이기잖아." 실제로 2024년 3월 공연법이 개정되어 **매크로를 이용한 관람권 매매는 1년 이하 징역 또는 1,000만원 이하 벌금**입니다. 인터파크는 임영웅 콘서트(40만 명 대기) 이후 다중 기기 접속 차단, 봇 탐지 강화 등 정책을 바꿨고요.

기술만으로 해결할 수 없는 문제는 비즈니스와 법으로 막는 겁니다.

### 그래서 예매 고수가 됐나?

솔직히 아직 멀었습니다. 이번에 알게 된 건 "왜 느린지", "어떤 방법들이 있는지" 정도예요.

실제 예매 사이트는 이 위에 **대기열 시스템**(Cloudflare Waiting Room, Redis Sorted Set 기반 가상 대기열), **Rate Limiting**(Token Bucket, Sliding Window), 그리고 **캡차**까지 얹혀 있습니다. 그건 다음 루프에서.

```java
do {
    연습하자();
} while (!예매고수);
```
