# Round-09: 상품 인기 랭킹 시스템 — 설계 논의 로그

## 1. 랭킹의 본질 정의

### 랭킹이란?
일렬로 늘어선 사람들이나 물건들을 의미한다. 상품, 브랜드, 키워드를 사용자(회원/비회원)에게 "이런 내용이 유행이라던데요?"라고 보여주는 것.

### 의도
사용자가 헷갈리지 않게끔 하기 위함. 일종의 **진입 장벽을 낮춰주는** 용도.

### 어원 리서치

**Rank**의 어원: 프랑크어 \*hring (고리/원) → 고대 프랑스어 ranc/rang (줄, 열) → 영어 rank (서열)

원래 의미는 "일렬로 늘어선 줄"이었다. 군대에서 병사들이 줄지어 선 모습(rank and file)이 시작점이고, 여기서 "그 줄 안에서의 위치 = 서열"로 의미가 확장됐다.

| 시기 | 맥락 | 핵심 이유 |
|------|------|-----------|
| 고대 그리스 (BC 776) | 올림픽 순위 | 경쟁 결과를 **한눈에** 보여주기 위해 |
| 중세 군대 (14~16C) | 병사 대열, 지휘 계급 | **복잡한 조직을 단순화**하기 위해 |
| 근대 (19~20C) | 스포츠, 대학, 빌보드 차트 | 선택지가 많아지면서 **판단 기준** 제공 |
| 디지털 (1998~) | PageRank, 이커머스 | 정보 폭발 시대의 **인지 부하 감소** |

### 불변의 본질

**"N개의 대상을 하나의 기준으로 줄 세워서, 보는 사람의 판단 비용을 줄여준다."**

이것은 어떤 도메인의 랭킹이든 동일하게 적용되는 사실이다.

## 2. 랭킹의 네 축

랭킹 시스템 설계의 불변 축 4가지를 정의했다.

| # | 축 | 질문 |
|---|---|------|
| 1 | **대상** | 무엇을 줄 세우는가 |
| 2 | **기준** | 무엇으로 줄 세우는가 |
| 3 | **소비자** | 누구에게 보여주는가 |
| 4 | **효과** | 왜 보여주는가 |

4번(효과)이 2번(기준)을 결정한다. 기대 효과가 다르면 같은 대상이라도 기준이 달라진다.

## 3. 네 축에 대한 의사결정

### 축 1: 대상 — 상품

### 축 2: 기준 — 인기 (종합 점수)

현재 시스템에 존재하는 지표 3가지:

| 지표 | 성격 | 의미 | 시스템 존재 여부 |
|------|------|------|-----------------|
| 조회수 | 관심 | 보긴 했다 | O |
| 좋아요 | 호감 | 마음에 든다 | O |
| 판매량 | 행동 | 실제로 샀다 | O |

관심 → 호감 → 행동 순으로 **전환 깊이**가 깊어진다.

**가중치 방향**: 판매량 > 좋아요 > 조회수 (전환 깊이가 깊을수록 강한 신호)

**초기값 결정 방식**: 논문/실험/기업 자료 리서치를 통해 근거 기반으로 결정 (아직 미수행)

**가중치는 설정값으로 분리**: 실 데이터가 쌓이면 조정할 수 있도록

### 축 3: 소비자 — 전체 (세분화는 고려만)

성별/연령 세분화 여부는 열어두되, 지금 결정하지 않는다. 설계 시 확장 가능하게만 고려.

### 축 4: 효과 — 순환하는 생태계

단순히 "지금 인기 있는 걸 보여준다"가 아니다.

**주기적으로 리셋되면서 순위가 바뀌는 것 자체가 목적**:
- 한 번 1등 한 상품이 영원히 1등이 아님
- 새 상품도 올라갈 기회가 생김
- 소비자 입장에서 "이번 주는 뭐가 뜨지?"라는 재방문 이유가 됨
- 전체적으로 상품 생태계가 **순환**한다

고정 랭킹이 아니라 **살아 움직이는 랭킹**.

## 4. 집계 범위와 갱신 주기

### 용어 정의

- **집계 범위 (Window)**: 어디서부터 어디까지의 데이터를 볼 것인가
- **갱신 주기 (Interval)**: 얼마나 자주 다시 계산할 것인가

### 윈도우 방식

| 방식 | 설명 | 특성 |
|------|------|------|
| **Tumbling Window** | 겹치지 않게 딱딱 끊는 방식 | 경계 시점에 순위가 한 번에 바뀜, 구현 단순 |
| **Sliding Window** | 겹치면서 밀려가는 방식 | 부드럽게 바뀜, 구현 상대적으로 복잡 |

```
Tumbling: |---1시간---|---1시간---|---1시간---|
            0:00~1:00  1:00~2:00  2:00~3:00

Sliding:  |---1시간---|
              |---1시간---|
                  |---1시간---|
            0:00    0:15    0:30
```

- Tumbling Window: 딱 끊고 새로 시작
- Sliding Window: 항상 "최근 N시간"을 보되 창이 밀려감. 오래된 데이터는 범위 밖으로 빠져나감

### 미결정 사항

집계 범위의 구체적 값(일간/주간 등)과 갱신 주기, 윈도우 방식은 아직 결정하지 않았다.

| | 무신사 | 29CM | 올리브영 | 쿠팡 |
|---|---|---|---|---|

| **실시간 지표** | "N명이 보는 중", "N명이 구매 중" | X | X | X |

### 인프라 아키텍처

| 서비스 | 핵심 |
|--------|------|
| **무신사** | Next.js SSR + 2단계 API (설정 API → 데이터 API) |
| **29CM** | 별도 `recommend-api` 서브도메인 — 랭킹을 추천 서비스로 분리 |
| **올리브영** | 서버리스 배치 (EventBridge → Glue → Athena → S3) — 사전 계산 |
| **쿠팡** | 내부 추천엔진 기반, 외부 노출 최소화 |

### 무신사 상세

- **API 구조**: 2단계 — 설정 API(`/pans/ranking`)가 UI 모듈 정의 반환, 데이터 API(`/pans/ranking/sections/{sectionId}`)가 실제 상품 데이터 반환
- **필터 파라미터**: `gf` (성별), `ageBand` (연령), `period` (기간), `categoryCode` (카테고리)
- **실시간 지표**: "X명이 보는 중", "X명이 구매 중" — 사회적 증거 활용
- **순위 변동**: 급상승(UP), 하락(DOWN), 유지(NONE) + 변동 폭 표시
- **스토어 분리**: musinsa, player(스포츠), beauty, boutique, outlet, sneaker, kids 각각 독립 랭킹
- **랭킹 아카이브**: 월별 과거 랭킹 조회 가능 (`/ranking/archive?date=YYYYMM`)

### 29CM 상세

- **API**: 별도 도메인 `recommend-api.29cm.co.kr`에서 랭킹 데이터 제공
  - `GET /api/v4/best/categories` — 카테고리 계층
  - `GET /api/v4/best/items` — 랭킹 상품 (limit=100, offset 기반 페이지네이션)
- **순위 표현**: 별도 rank 필드 없음. 배열 순서가 곧 순위
- **성별 파라미터**: API에 `gender` 파라미터 존재하나 현재 UI에서 미노출 (항상 null)
- **기간 필터**: `NOW`(실시간), `ONE_DAY`(일간), `ONE_WEEK`(주간), `ONE_MONTH`(월간)
- **카테고리**: 3 depth (대/중/소), 총 20개 대분류
- **좋아요**: `heartCount`, `heartOn` 필드로 좋아요 수 및 현재 사용자의 좋아요 여부 제공

### 올리브영 상세

- **이중 랭킹**: 판매 랭킹(시간별 갱신)과 브랜드 랭킹(주간 갱신)을 분리 운영
- **인프라**: AWS 서버리스 배치 파이프라인
  - Amazon EventBridge → 스케줄 트리거
  - AWS Glue → 원시 데이터 수집, Parquet으로 S3 저장
  - Amazon Athena → 집계 쿼리 실행
  - 결과를 S3에 시간 단위/집계 로직별로 저장
  - 필터 조합 수 = 병렬 처리 브랜치 수
- **랭킹 API**: `product-ranking-service.oliveyoung.com` (별도 서비스)
- **카테고리**: 뷰티(12개), 건강/식품(5개), 라이프스타일(3개) = 총 21개
- **뱃지 시스템**: 세일, 쿠폰, 증정, 오늘드림(당일배송) — 1급 데이터 필드로 관리

### 쿠팡 상세

- **봇 차단**: User-Agent 분석, IP 패턴 감지, Rate Limiting으로 자동화 접근 차단 (403 반환)
- **정렬**: `sorter=bestAsc`로 베스트셀러 순 정렬
- **랭킹 노출 점수 구성**: 배송일, 상품 점수, 가격 경쟁력
- **Coupang Partners API** (제휴 API):
  - `bestCategoryProducts` — 카테고리별 베스트 상품
  - `goldbox` — 일일 특가
  - 응답에 `rank`, `isRocket`, `isFreeShipping` 필드 포함
- **성별/연령**: 소비자 UI에 노출하지 않음. 내부 추천 엔진이 로그인 컨텍스트와 브라우징 히스토리 기반으로 처리

### 우리 설계에 참고할 포인트

1. **집계 범위**: 4곳 중 3곳이 실시간/일간/주간/월간 제공 — 최소 일간/주간은 있어야 함
2. **성별/연령**: 무신사만 본격 지원, 나머지는 미노출 — 3번 축 세분화는 후순위 판단이 타당
3. **랭킹은 사전 계산**: 요청 시 실시간 계산이 아니라 미리 계산해두고 조회만 하는 구조
4. **배열 순서 = 순위**: 별도 rank 필드 없이 정렬된 결과를 그대로 내려주는 것도 방법

산출 근거: 무신사/29CM 실데이터 역산 + 패션 이커머스 업계 벤치마크

| 지표 | 일일 건수 | 산출 방식 |

| **주문** | ~2.2만~4.5만 | DAU의 3~6% 주문 |
| **랭킹 페이지 조회** | ~225만~280만 | 전체 페이지뷰의 20~25% |

### DAU 구간별 추정치

| DAU | 상품 조회 | 좋아요 (7%) | 주문 (4.5%) | 랭킹 조회 (22%) |
|-----|----------|-----------|-----------|---------------|
| 50만 | 280만 | 19.6만 | 2.25만 | 165만 |
| 75만 | 420만 | 29.4만 | 3.38만 | 248만 |
| 100만 | 550만 | 38.5만 | 4.5만 | 330만 |

### 피크 시간 TPS (20~23시, 일 트래픽의 40~50% 집중)

| 항목 | 피크 평균 TPS | 성격 |
|------|-------------|------|
| 상품 조회 | ~78 | 읽기 |
| 랭킹 조회 | ~47 | 읽기 |
| 좋아요 쓰기 | ~6 | 쓰기 |
| 주문 쓰기 | ~0.6 | 쓰기 |

### 랭킹 설계에 주는 시사점

- 랭킹 **계산 입력 데이터**: 하루 기준 조회 420만 + 좋아요 30만 + 주문 3만 → 일 단위 집계도 충분한 볼륨
- 랭킹 **조회 트래픽**: 피크 ~47 TPS → 사전 계산 + 캐시로 충분히 처리 가능
- 좋아요/주문 **쓰기 TPS**는 낮으므로 (6 + 0.6 TPS) 실시간 점수 반영은 부담 없음

### 주요 리서치 출처

- 무신사: MAU 549만(2024 H1), 연 GMV 4.5조, 블프 피크 720 TPS
- 29CM: MAU 234만, 연 GMV 1조+, AOV 23만원
- 패션 이커머스 벤치마크: 세션당 8~10페이지, PDP 비율 35~40%, 좋아요율 5~10%, 전환율 3~6%
- 랭킹 페이지 비중: 전체 페이지뷰의 20~25% (무신사 "랭킹은 유저가 가장 먼저 방문하는 페이지")

## 7. 기존 코드 현황 분석 — 랭킹 입력 데이터

### 핵심: ProductMetrics 테이블에 3개 지표가 이미 모여있음

```
product_metrics (테이블)
├── productId (unique)
├── viewCount    ← 조회수
├── likesCount   ← 좋아요 수
└── salesCount   ← 판매량
```

### 각 지표별 데이터 흐름

| 지표 | 발행 시점 | 이벤트 | Kafka 토픽 | 최종 저장 |
|------|----------|--------|-----------|----------|
| **조회수** | ProductService.getById() | ProductViewedEvent | `product-view-events` | ProductMetrics.viewCount++ |
| **좋아요** | LikeMarkService.mark/unmark() | ProductLiked/UnlikedEvent | `product-like-events`, `product-unlike-events` | ProductMetrics.likesCount ±1 |
| **판매량** | OrderService.create() | OrderCreatedEvent (Outbox) | `product-order-events` | ProductMetrics.salesCount += quantity |

### 이벤트 처리 아키텍처

```
Domain Event 발행 (Application Layer)
    ↓
@TransactionalEventListener (AFTER_COMMIT)
    ↓
MetricsKafkaEventListener → Kafka 전송
    ↓
commerce-streamer 모듈에서 Consumer 수신
    ↓
EventProcessor가 ProductMetrics 업데이트
    ↓
EventHandled 테이블로 멱등성 보장
```

### 비정규화 현황

| 필드 | 위치 | 용도 | 비고 |
|------|------|------|------|
| Product.likesCount | Product 엔티티 | 정렬 (LIKES_DESC) | 인덱스 있음 (`idx_product_likes`) |
| ProductMetrics.likesCount | ProductMetrics | 분석/집계 | Kafka 비동기 업데이트 |
| ProductMetrics.viewCount | ProductMetrics | 분석/집계 | Product 엔티티에는 없음 |
| ProductMetrics.salesCount | ProductMetrics | 분석/집계 | 취소 시 차감 안 함 (역사적 기록) |

### 랭킹 구현 시 부족한 것 — 핵심 의사결정 포인트

**현재 ProductMetrics는 전체 누적값만 저장한다.**

- "총 조회수 5만", "총 좋아요 3천", "총 판매 800개" ← 이것만 있음
- "오늘 조회수 200", "이번 주 좋아요 50" ← 이것은 없음

4번 축에서 정한 **"순환하는 생태계"** 를 구현하려면, 기간별 집계(일간/주간)가 필요하다. 누적값만으로는 한 번 1등이 영원히 1등이 되어 순환이 불가능하다.

**→ 시간 윈도우 기반 집계 구조가 추가로 필요하다. 이 구조를 어떻게 설계할지가 다음 논의 대상.**

가능한 방향:
1. **이벤트 로그 테이블** — 개별 이벤트를 시간 정보와 함께 저장하고, 배치로 기간별 집계
2. **기간별 스냅샷 테이블** — 일간/주간 단위로 미리 집계해서 별도 테이블에 저장
3. **Redis 시간 기반 구조** — Sorted Set + 시간 스코어로 기간별 카운트 관리

## 8. 집계 구조 설계 — 시간 버킷 vs 이벤트 로그

### product_metrics의 역할 재정의

`product_metrics`는 업계에서 **현재 상태 요약 (1상품 = 1행, 누적 카운터)** 으로 사용하는 것이 관례.
시간 기반 집계가 필요할 때는 별도 테이블을 추가하는 것이 표준 패턴. (Magento, 올리브영, 무신사 등)

→ **product_metrics는 누적 카운터로 유지**, 시간 버킷 테이블을 별도 추가.

### 두 방식 비교

| | 시간 버킷 (product_metrics_daily) | 이벤트 로그 (개별 행) |
|---|---|---|
| **장점** | 집계 빠름, 용량 적음, 월간 합산 가능 | 실시간 유연성, 임의 구간 분석 가능 |
| **단점** | 단위 변경 시 테이블 추가 | 일 450만 행, 월간 집계 불가, 스케줄링 정리 필요 |
| **일간** | 10만 × 30일 = 300만 행/월 | 450만 × 30일 = 1.35억 행/월 |
| **시간별** | 10만 × 24 × 30 = 7,200만 행/월 (파티셔닝) | 동일 |
| **월간** | daily 30행 합산 | 1.35억 행 스캔 (비현실적) |

### 결정: 시간 버킷

랭킹은 본질적으로 **"고정 구간의 합계"** 만 필요하다. 이벤트 로그가 강한 임의 구간 분석("최근 47분")은 랭킹이 아니라 분석 시스템의 관심사.

```
일간:   product_metrics_daily   → 300만 행/월 (파티셔닝)
시간별: product_metrics_hourly  → 7,200만 행/월 (파티셔닝, 추후)
월간:   daily 합산으로 계산     → 추가 테이블 불필요
```

### 전체 아키텍처

```
Kafka 이벤트
    ↓ Consumer
    ├── DB: product_metrics (누적 카운터, 기존 유지)
    ├── DB: product_metrics_daily (일간 집계, 월별 파티셔닝)
    └── Redis: Sorted Set (랭킹 서빙용, 날짜 키)

배치 (하루 1회, 0시 20분)
    ├── "어제" product_metrics_daily에서 가중치 적용해 점수 계산
    └── Redis Sorted Set 갱신 → 오늘 하루 동안 서빙

Redis 장애 시
    └── product_metrics_daily에서 재계산 → Redis 복구
```

### 배치 스케줄

```
0시 00분 — LikesCountSync (기존)
0시 20분 — 랭킹 배치 (신규) — "어제" 전체 데이터 기준
1시 00분 — EventCleanup (기존)
```

LikesCountSync 소요시간을 10분으로 추정, 2배 마진 = 20분 후 랭킹 배치 시작.

### 감쇠/이월 — 일간에서는 불필요

일간 랭킹은 **어제 하루 전체(완전한 24시간)** 를 집계하므로:
- 데이터 부족 문제 없음 (항상 완결된 데이터)
- 감쇠/이월 불필요 — 매일 완결된 데이터로 새로 계산
- 콜드스타트 없음 — 어제 하루 전체가 근거

### 🔍 리뷰 포인트 1: 이벤트 로그 방식 재고려

시간 버킷으로 결정했으나, **집계 단위가 10분 이하로 내려가면** 시간 버킷의 한계가 드러날 수 있다.

- 10분 단위 시간 버킷: 10만 × 144(하루) × 30일 = **4.3억 행/월** → 사실상 이벤트 로그와 차이 없음
- 이 시점에서는 이벤트 로그 + 스케줄링 정리가 오히려 단순할 수 있음
- 시간 버킷은 "빈 구간도 행이 생기는" 오버헤드가 있지만, 이벤트 로그는 활동 있는 것만 쌓임

**분기점: 집계 단위가 1시간 이상이면 시간 버킷 유리, 10분 이하면 이벤트 로그 재검토 필요.**

추후 초 실시간(시간 단위) 구현 시 이 트레이드오프를 다시 평가할 것.

### 🔍 리뷰 포인트 2: 초 실시간에서의 감쇠/콜드스타트/데이터량 트리거

일간 랭킹에서는 "어제 전체"를 쓰므로 감쇠가 불필요하지만, **1시간/10분 단위로 내려가면** 직전 윈도우 데이터가 부족한 구간이 발생한다.

이때 검토할 세 가지 전략:

1. **감쇠 이월**: 직전 윈도우 점수의 N%를 가져감 — 단, 비율이 높으면 1등이 영원히 안 꺾이는 문제
2. **데이터량 기반 전환**: 충분한 데이터가 쌓일 때까지 이전 랭킹 유지, 임계치 도달 시 새 랭킹으로 교체
3. **하이브리드**: 데이터 부족 시 이전 랭킹 유지 + 충분하면 전환 (감쇠 없이)

**참고 — 무신사 실시간 랭킹 관찰**: 갱신 주기가 10분일 때도 있고 20분일 때도 있음. 추측하건대, 데이터가 충분하지 않다고 판단되면 갱신을 건너뛰는 방식일 가능성이 있음. 즉 **고정 주기가 아니라 데이터 충분성 기반으로 갱신 여부를 결정**하는 것으로 보임.

→ 초 실시간 구현 단계에서 이 세 전략을 비교 평가할 것.

4. 모든 업계 실무자가 "보수적으로 시작, A/B 테스트로 튜닝" 권장

## 10. 조회수 어뷰징 방어 — PV vs UV 분리

### 문제

현재 조회수는 모든 요청을 카운트(PV)하며, 어뷰징 방어가 전혀 없다.

- `ProductController.getById()` — 인증 헤더 없음 (비회원 접근 가능)
- `ProductViewedEvent.of(id, null)` — memberId가 항상 null
- `ProductMetrics.incrementViews()` — 무조건 +1

가중치 10:3:1로 잡아도 일일 점수 기여는 조회가 78%를 차지한다:
- 조회 420만 × 1 = 420만 점
- 좋아요 30만 × 3 = 90만 점
- 판매 3만 × 10 = 30만 점

새로고침만 반복해도 순위를 올릴 수 있는 구조.

### 의사결정: ProductMetrics와 랭킹 점수 계산을 분리한다

| 구분 | ProductMetrics | 랭킹 점수 계산 |
|------|---------------|--------------|
| **목적** | 통계/분석 (있는 그대로) | 인기 순위 산출 |
| **조회수** | 모든 요청 카운트 (PV) | 유니크 조회수 (UV) |
| **좋아요** | 누적 총합 | 기간 내 집계 |
| **판매량** | 누적 총합 | 기간 내 집계 |

**근거:**
- ProductMetrics는 순수 통계 목적 → 기존 코드를 건드리지 않음
- 랭킹은 별도 집계 구조에서 UV 기반 + 기간 윈도우로 계산
- 어차피 "순환하는 생태계"(4번 축)를 위해 기간별 집계가 필요 → 거기서 UV 중복 제거까지 함께 해결

### 비회원 조회 처리

상품 조회 API는 비회원도 접근 가능 (비즈니스적으로 맞음). 따라서:
- **회원**: memberId 기반 UV 중복 제거
- **비회원**: IP 기반 중복 제거, 또는 로그 스케일 감쇠로 볼륨 억제

### 다음 논의 대상

- UV 중복 제거의 구체적 구현 방식 (Redis Set? 시간 버킷 테이블에 unique 제약?)
- 비회원 식별 전략 확정 (IP? 디바이스 핑거프린트?)

## 11. 가중치 심화 — 로그 스케일 + 집계 범위별 전략

### 문제: UV만으로는 볼륨 격차가 해소되지 않는다

UV 중복 제거 후에도 일일 수치(인기 상품 1개 기준):
- 조회 UV: 5,000 / 좋아요: 350 / 판매: 35
- 비율 = 143 : 10 : 1

가중치 10:3:1을 곱해도 조회가 53%를 차지 → 가중치의 의도(판매 > 좋아요 > 조회)가 무력화됨.

**UV = 어뷰징 방어, 로그 = 볼륨 격차 완화. 목적이 다르므로 둘 다 필요.**

### 검토한 로그 적용 방식

| 방식 | 결과 | 문제 |
|------|------|------|
| 조회만 로그 | 조회 0.3%, 좋아요 75%, 판매 25% | 조회가 사라짐 |
| 조회만 로그 + 가중치 재조정 | 직관에 반하는 가중치 (조회 W가 판매보다 높아야 함) | 복잡하고 혼란 |
| **세 지표 전부 로그** | 조회 14%, 좋아요 28%, 판매 58% | **가중치 의도대로 동작** |

### 로그의 단점과 대응

**단점**: 적은 값 구간에서 차이가 뭉개짐
- 좋아요 2개 vs 5개 = 2.5배 차이 → 로그 후 0.30 vs 0.70 = 차이 축소

**대응**: 집계 범위에 따라 로그 적용 여부를 분리

| 집계 범위 | 데이터 볼륨 | 로그 적용 | 근거 |
|----------|-----------|----------|------|
| **일간/주간** | 큼 (조회 수천~수만) | O | 볼륨 격차 완화 필요, 뭉개져도 충분한 데이터 |
| **초 실시간 (1시간/10분)** | 작음 (조회 수십~수백) | X | 미세 차이 보존 필요, 볼륨 자체가 작아 격차 문제 없음 |

**일관된 원칙: 볼륨이 크면 로그로 눌러주고, 볼륨이 작으면 그대로 둔다.**

### 의사결정: 일간 랭킹 점수 공식

```
score = 10 × log10(판매 + 1) + 3 × log10(좋아요 + 1) + 1 × log10(조회UV + 1)
```

- `+1`은 log(0) = -∞ 방어
- 가중치 10:3:1은 설정값으로 분리하여 추후 조정 가능

### 검증 (인기 상품 일일 수치)

| 지표 | 원시값 | log10(값+1) | × 가중치 | 점수 | 비중 |
|------|--------|------------|---------|------|------|
| 조회 UV | 5,000 | 3.7 | × 1 | 3.7 | 14% |
| 좋아요 | 350 | 2.5 | × 3 | 7.6 | 28% |
| 판매 | 35 | 1.5 | × 10 | 15.4 | **58%** |
| | | | **합계** | **26.7** | 100% |

판매 58% > 좋아요 28% > 조회 14% → 가중치 의도에 부합.

### 초 실시간 랭킹 점수 공식 (추후 구현 시)

```
score = 10 × 판매 + 3 × 좋아요 + 1 × 조회UV
```

로그 미적용. 볼륨이 작아 격차 문제가 없고, 1개 차이가 순위를 가를 수 있으므로 미세 차이 보존.

## 12. 구현 중 발견한 이슈 — unlike 크로스데이 문제

### 문제

1일에 좋아요, 2일에 취소하면:
- `ranking:all:20260401` → +3 (1일에 받은 혜택)
- `ranking:all:20260402` → -3 (2일에 페널티)

2일 ZSET에서 해당 상품이 마이너스 점수가 된다. 1일에 받은 혜택은 그대로인데 2일에 페널티를 받는 구조.

### 검토한 방안

| 방안 | 설명 | 복잡도 |
|------|------|--------|
| A. unlike은 랭킹에 반영 안 함 | like만 +3, unlike 무시 | 단순 |
| B. 같은 날 like한 경우만 차감 | 오늘 누른 좋아요만 취소 가능 | 중간 |
| **C. 원래 날짜의 ZSET에서 차감** | 1일 ZSET에서 -3 | 복잡하지만 정확 |

### 결정: C안 — 원래 좋아요 날짜 기준 차감

**구현 방식:**
- `ProductUnlikedEvent`에 `likedDate(LocalDate)` 필드 추가
- `LikeMarkService.unmark()`에서 Like 삭제 전 `createdAt`을 읽어 `LocalDate`로 반환
- `LikeService.unlike()`에서 likedDate를 이벤트에 전달
- `LikeEventProcessor`에서 unlike 시 `likedDate` 기준 날짜 키로 ZSET 차감

**null-safety:** 테스트 환경에서 BaseTimeEntity.createdAt이 null일 수 있으므로 (JPA persist 전) fallback으로 `LocalDate.now()` 사용.

## 13. 랭킹 API — 상품정보 Aggregation

### 문제

과제 요구사항: "랭킹 Page 조회 시 단순히 상품 ID가 아닌 상품정보가 Aggregation 되어 제공된다"

초기 구현에서 `RankingApiResponse`가 productId/score/rank만 반환. 상품명, 가격, 브랜드명이 없으면 클라이언트가 추가 호출 필요.

### 결정: RankingService에서 일괄 조회

```
ZSET에서 Top-N productId 목록
    ↓
ProductRepository.findAllByIdIn(productIds) → Map<Long, Product>
    ↓
BrandRepository.findAllByIdIn(brandIds) → Map<Long, Brand>
    ↓
RankedProduct + Product + Brand → RankingInfo
```

- N+1 없이 IN 쿼리 2번으로 해결 (상품 1회, 브랜드 1회)
- RankingInfo에 productName, price, brandName 추가
- 삭제된 상품이 ZSET에 남아있어도 product=null로 처리 (NPE 방지)

- **집계와 로그**: 이벤트 핸들링 테이블 vs 로그 테이블 분리의 의미, Round 7에서 힌트가 있었음

- **가중치 결정의 어려움**: 실 데이터 없이 어떻게 초기값을 정하는가 — 퍼널 역수, EdgeRank 참고
- **unlike 크로스데이**: 일간 윈도우에서 좋아요 취소가 다른 날짜에 일어났을 때의 문제

## 15. 랭킹 시스템의 본질

**랭킹 시스템 = 집계 + 순서.** 이게 전부다.

- **집계**: 이벤트를 모아서 점수를 매기는 것 (무엇을, 어떤 기준으로, 어떤 범위에서)
- **순서**: 그 점수로 줄 세우는 것 (Redis ZSET이 담당)

순서 쪽은 ZSET이 거의 다 해결해주고, 어려운 건 전부 집계 쪽이었다.
초 실시간 랭킹도 마찬가지 — 집계를 바꾸면 순서는 따라온다.

## 16. 초 실시간 (시간 단위) 랭킹 설계

### 구조: daily와 hourly 병행

| | daily | hourly |
|---|---|---|
| **목적** | 오늘의 인기상품 | 지금 뜨는 상품 |
| **Redis 키** | `ranking:daily:{yyyyMMdd}` | `ranking:hourly:{yyyyMMddHH}` |
| **Redis TTL** | 2일 | 24시간 |
| **DB 백업** | product_metrics_daily | product_metrics_hourly |
| **DB 보관** | 월 단위 파티셔닝 | 3일 (스케줄러 정리) |

Processor에서 이벤트마다 ZINCRBY를 **2번** — daily 키, hourly 키 각각.

### TTL 결정 근거

hourly Redis 24시간으로 잡은 이유:
1. hourly 24개 합산 → daily 검증/복구 가능
2. 콜드 스타트 carry-over 전략 실험 여유 — 직전 N시간 데이터 필요
3. 가중치 미확정이므로 넉넉하게 잡고 나중에 줄이는 방향

**추후 검토**: carry-over 전략이 확정되면 TTL을 더 짧게 가져갈 수 있음.

### DB 보관 3일 근거

- 3일: 10만 × 24 × 3 = 720만 행 (가벼움)
- Redis 장애 복구 + 디버깅 여유
- 스케줄러로 3일 지난 데이터 삭제

## 17. 콜드 스타트 — Carry-Over 설계

### 문제

시간 단위 랭킹은 매 정각에 새 ZSET이 생기며 0점에서 시작. 17시 01분에 조회 1건이면 그 상품이 1등 — 의미 없는 순위.

### Carry-Over란

이전 구간의 점수를 다음 구간으로 **이월**하는 것. 회계의 "이월 잔액"과 같은 개념.

```
EMA 공식: S(t) = α × V(t) + (1 - α) × S(t-1)
- α = 새 데이터 반영률
- (1-α) = carry-over 비율
```

### 실서비스 carry-over 비율 리서치

| 시스템 | 윈도우 | carry-over | 반감기 |
|--------|--------|-----------|--------|
| Hacker News | 연속 | ~49% (초기) | ~1시간 |
| Reddit Hot | 연속 | ~83%/시간 | ~12.5시간 |
| Amazon BSR | 1시간 | ~97%/시간 | ~23시간 |
| Twitter 트렌딩 | ~15분 | ~25-35%/시간 | ~30-60분 |
| 멜론 (개편 전) | 1시간 | 현재 60% + 24시간 누적 40% | 하이브리드 |

### 반감기 테이블

| carry-over | 반감기 | 4시간 후 잔존 | 적합 상황 |
|-----------|--------|-------------|----------|
| 0.2 | 26분 | 0.16% | 트위터형 초공격적 |
| **0.5** | **1시간** | **6.25%** | **시간 단위 랭킹 (채택)** |
| 0.8 | 3.1시간 | 41% | 일간 스케일 |
| 0.97 | 23시간 | 89% | 아마존 BSR형 |

### 결정: carry-over 0.5 (반감기 1시간)

**근거:**
1. 1시간 단위 랭킹이니까 반감기도 1시간이 직관적
2. 4시간 후 이전 영향 6.25% → 사실상 사라짐
3. 보수적으로 시작, 실 데이터 보고 조정 가능

**동작:**
```
16시 종료 시: 상품A 150점, 상품B 80점
17시 시작 시 (carry-over):
  상품A: 75점 (150 × 0.5)
  상품B: 40점 (80 × 0.5)
  → 17시 활동이 쌓이면서 carry-over 비중 감소
18시 시작 시:
  상품A의 16시 기여분: 37.5점 (150 × 0.25)
  → 2시간 뒤 원래 영향의 25%만 남음
```

### 스케줄: 매 정각 실행

```
매 정각     — HourlyRankingCarryOverScheduler
              이전 시간 ZSET 전체 → 점수 × 0.5로 새 시간 ZSET에 이월
0시 00분    — LikesCountSync (기존)
0시 20분    — DailyRankingRecoveryScheduler (daily 복구)
1시 00분    — EventCleanup (기존)
1시 30분    — HourlyMetricsCleanupScheduler (3일 지난 hourly 삭제)
```

### 추후 검토

- carry-over 0.5가 적절한지 실 데이터로 검증 필요
- 직전 1시간만 carry-over vs 여러 시간 감쇠 합산 비교
- TTL 24시간을 줄일 수 있는지 carry-over 전략 확정 후 재평가

| 6 | **신호 품질** | 조작된 신호를 어떻게 걸러내느냐 | PV→UV, 봇 탐지, 속도 이상 감지 |

## 19. 5번 축 구현 — 정규화 (log 스케일)

### 핵심 문제: log는 누적값에 적용해야 한다

이벤트 단위로 ZINCRBY 하면서 log를 적용할 수 없다:
```
조회 100건 → log10(101) = 2.0        ← 전체에 log (올바름)
조회 1건씩 100번 → log10(2) × 100 = 30.1  ← 건건이 log (잘못됨)
```

### 결정: daily와 hourly 집계 방식 분리

| | daily | hourly |
|---|---|---|
| **log 적용** | O (볼륨 격차 완화) | X (미세 차이 보존) |
| **ZSET 갱신** | 배치 (0시 20분) | 실시간 ZINCRBY |
| **점수 공식** | `10×log10(판매+1) + 3×log10(좋아요+1) + 1×log10(조회+1)` | `10×판매 + 3×좋아요 + 1×조회` |

### 아키텍처 변화

**Before:**
```
이벤트 → Processor → DB 적재 + ZINCRBY (daily + hourly 건건이)
```

**After:**
```
이벤트 → Consumer 배치 수신 (최대 3000건)
           ↓
         for문: Processor.process(record)
           ├── DB 적재 (ProductMetrics, Daily, Hourly)
           └── return productId + score
           ↓
         Consumer가 HashMap에 상품별 합산 (메모리)
           ↓
         합산 결과로 ZINCRBY (hourly만, 상품 수만큼)

별도:
  배치 스케줄러 (0시 20분)
    → product_metrics_daily에서 어제 누적값 읽기
    → log10 적용해서 점수 계산
    → ZSET daily에 저장
```

### 배치 합산 최적화 (Kafka 배치 리스너 활용)

기존: 3000건 → ZINCRBY 3000번
개선: 3000건 → 상품별 합산 → ZINCRBY N번 (상품 수만큼)

Consumer가 이미 배치 리스너(최대 3000건, 1MB or 5초)로 동작하고 있었으나, Processor 내부에서 건건이 Redis를 호출하고 있었음. Processor에서 Redis 의존을 제거하고 Consumer에서 배치 합산 후 한 번에 Redis에 쓰도록 변경.

### Processor 역할 변경

| | Before | After |
|---|---|---|
| **책임** | DB 적재 + Redis ZINCRBY | DB 적재만 |
| **반환값** | void | productId + score (Consumer에서 합산용) |
| **Redis 의존** | 있음 | 없음 |

## 20. 6번 축 구현 — 신호 품질 (UV 중복 제거)

### 문제

현재 조회수가 PV(모든 요청 카운트) → 새로고침만 반복해도 랭킹 점수가 올라감.

### UV 체크 방식 검토

| 방식 | 중복 확인 | 메모리 | 속도 | 정확도 |
|------|----------|--------|------|--------|
| Redis Set | O | 큼 | 빠름 | 정확 |
| HyperLogLog | X (총 수만) | 극소 (12KB) | 빠름 | 근사치 |
| DB unique | O | 없음 | 느림 | 정확 |

HyperLogLog는 "이 회원이 봤는지" 개별 확인 불가 → 탈락.

### 메모리 계산

일간 Redis Set: 75만 DAU × 5.6 상품 = 420만 쌍 × 100bytes ≈ **400~500MB** → 부담

시간별 Redis Set: 420만/24 ≈ 17.5만 쌍 × 100bytes ≈ **17.5MB** (피크 ~50MB) → 부담 없음

### 결정: 시간별 Redis Set + TTL 2시간

```
키:  viewed:hourly:{yyyyMMddHH}:{productId}
값:  {memberId1, memberId2, ...}
TTL: 2시간
메모리: ~50MB (피크)
```

| | UV 체크 방식 | 메모리 |
|---|---|---|
| hourly | Redis Set (SADD + SISMEMBER, TTL 2시간) | ~50MB |
| daily | 배치에서 DB 기반 집계 (이미 중복 제거된 hourly 데이터) | 0 |

### 비회원 처리

memberId가 null인 경우 UV 체크를 건너뛰고 카운트 허용. 추후 IP 기반 제한 가능.

## 21. 7번 축 검토 — 후처리 (다양성/비즈니스 룰)

### 검토한 후처리 후보

| 후처리 | 검토 결과 |
|--------|----------|
| **삭제 상품 제외** | 이미 DB 조회 시 product=null → 사실상 제외됨 |
| **품절 상품** | stock=0으로 내려감 → 클라이언트가 판단 가능. 4번 축(순환) 관점에서 품절 상품이 1등을 계속 차지하면 문제이나, 표시로 충분 |
| **브랜드 다양성** | 현실적으로 지키기 어려움, 데이터 부족 |

### 결정: 추가 코드 없이 현재 상태 유지

현재 RankingService에서 상품 정보를 DB 조회하는 과정에서:
- 삭제 상품: product=null (이름/가격 없이 내려감 → 사실상 제외)
- 품절 상품: stock=0 정보 포함 (클라이언트 판단)

별도 후처리 로직 불필요. 추후 카테고리 세분화나 비즈니스 요구가 생길 때 재검토.

## 23. 랭킹 점수 반영 시점 — ACCEPTED → PAID 변경

### 문제

기존: 주문 생성(ACCEPTED) 시 salesCount + 랭킹 점수 반영 → 결제 전 취소해도 점수 유지

### 결정: PAID 시점으로 변경

돈을 낸 게 진짜 판매. OrderPaidEvent를 신규 생성하고 결제 완료 시 발행.

```
Before: 주문(ACCEPTED) → 점수 ↑ → 취소해도 유지
After:  주문(ACCEPTED) → 아무것도 안 함
        결제(PAID)     → 점수 ↑
        취소(CANCELLED) → 차감 불필요 (PAID 전에만 취소 가능하므로 점수가 올라간 적 없음)
```

### 구현

- `OrderPaidEvent` 신규 — orderId, memberId, orderLines(productId, quantity)
- `OrderCancelledEvent` 보강 — orderLines + orderedDate 추가 (추후 환불 시 사용 대비)
- `OrderPaymentEventListener` — pay() 후 OrderPaidEvent 발행
- `OrderActivityEventListener` — OrderPaidEvent → Outbox 저장
- `OrderEventProcessor` — ORDER_PAID만 처리, ORDER_CANCELLED 차감 로직 제거

### 추후 검토

PAID → REFUNDED 흐름이 추가되면 환불 시 랭킹 차감 구현 필요.
OrderCancelledEvent에 orderLines + orderedDate를 미리 추가해둔 것은 이때를 대비한 것.

### 전체 흐름 테스트 (이벤트 → Kafka → Consumer → ZSET → API)

Docker 불안정으로 commerce-streamer 기동 실패. Docker 안정화 후 재시도 필요.

검증된 구간과 미검증 구간:
```
[검증됨] 상품 조회 → ProductViewedEvent 발행 → MetricsKafkaEventListener → Kafka 전송

[검증됨] Redis ZSET → Ranking API → 상품정보 Aggregation 응답
```

미검증 구간은 Processor 단위 테스트 + Consumer 통합 테스트로 보완 가능.
